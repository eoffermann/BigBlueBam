## 1. FTUE fix (DONE, verified) — the original ask

**Problem:** the first-time-user Settings tour kept reappearing on every login even
after you skipped it.

**Root cause:** the skip path *did* persist `notification_prefs.ftue_completed = true`
to the DB correctly (proven end-to-end against the live stack). But the
`POST /auth/login` response omitted `notification_prefs`, returning only
`id/email/display_name/role/org_id/is_superuser/active_org_id`. The SPA replaces
its store user with that partial object, and `App` computes `ftueRequired`
directly from it, so `ftue_completed` read as `undefined` and the tour re-fired on
every login. `fetchMe()` (which does return `notification_prefs`) only runs once on
mount, so the partial login user is what the gate saw until a full page reload.

**Fix (`a71da81f`):** the login response now carries the same identity fields
`GET /auth/me` returns: `notification_prefs`, `force_password_change`, `timezone`,
`kind`. Backend-only. Verified live: a user with `ftue_completed=true` now gets
`ftueRequired=false` immediately at login. This also fixes a sibling latent bug
(the forced-password-change redirect was likewise blind right after login).

**Options:**

- [x] Approve the fix as-is.
- [ ] Also add a frontend safety net (call `fetchMe()` right after login) as defense-in-depth.
- [ ] Revert it / I want a different approach.

green on `e14e1901`. No code behavior change; this is lint configuration only.

requires a **delta migration** (the repo has `scripts/build-permission-delta.mjs`

needs careful review of the renames before it lands in production.
