## Design

**Round-2 verification:** all seven fixed in the text. design-1 (§2.3 `pass_with_exception` under Not met with a "risk accepted" sub-count and no gap; §2.6 `frozen_refs`, 90/365-day caps, approver differs from proposer; §2.7 step 6 cap at `medium`; §11.3 gate); design-2 (§2.3 "Not set up yet" count and denominator on every surface, `not_assessed` gap after 14 days or at once when all assertions are rejected, auditor room "Not assessed"); design-3 (§2.3 one org-level stale row derived at read time, no template; §2.7 step 8 stored status only); design-4 (§3.1 NULL means "unknown", predicate still runs, Redeliver note, seed M4 covers NULL); design-5 (§3.3 redaction withdraws and re-evaluates); design-6 (§3.1 `population_unlisted`, `population_drift` and `population_review` gaps, §2.1 step 4 complete-list confirmation); design-7 (§2.1 per-requirement applicability, derived control value, `statement_of_applicability.csv`, packet blocked until every requirement has a decision; retirement on framework archive covered).

1. **[design] MAJOR - `effectiveStatus` applies exceptions to the control's worst-of status, so an exception on one failing assertion hides an unprovable sibling assertion.**
   - Where: §3.2, the `effectiveStatus` definition ("else `pass_with_exception` when exceptions cover every failing ref, else the stored status"); §2.2 (stored status is worst-of).
   - Why it matters: Take a control with assertion A `fail` and fully covered by an exception, and assertion B `unprovable/manual_evidence_missing`. Stored status is `fail` (worst-of), every failing ref is covered, so the function returns `pass_with_exception`. The control then reads "Not met, risk accepted" instead of "Can't prove yet". Per the §2.3 table, `pass_with_exception` produces no gap, so B's `manual_missing` gap and its `evidence_request` fix drop off the flagship list. The questionnaire also caps the answer at `medium` when it should force `low`. A literal implementation of the text produces this bug.
   - Fix: Apply exceptions per assertion, then aggregate. Each failing assertion becomes `pass_with_exception` when its failing refs are covered. Control effective state is the worst-of over those per-assertion states, ordered `fail` > `unprovable` > `pass_with_exception` > `pass`. Gaps are computed per assertion from the same per-assertion states. Add the §11.1 case "covered fail plus unprovable sibling gives Can't prove yet, and the `manual_missing` gap is present".

2. **[design] MAJOR - When an exception expires, the control goes back to Not met but no drift event or task follows, because drift fires only on stored-status changes.**
   - Where: §2.5 ("Worsening **stored** status ... writes a `bastion_drift_events` row"), §2.6 ("Expiry publishes `exception.expired` and the effective state reverts"), §7 `bastion-evidence-expiry`.
   - Why it matters: Stored status stays `fail` for the whole life of the exception, so expiry changes only the effective state. No drift row, no `control.drifted` event, and no task upsert or reopen happen. While the risk was accepted, people will reasonably close the Bam task. At expiry the control silently returns to Not met with nothing in anyone's queue. That is the retention failure that round-1 design-6 fixed for ordinary drift, and `exception.expired` reaches only orgs that have built a Bolt rule for it.
   - Fix: When an exception expires (or is revoked) and the control's effective state worsens, the expiry job writes a `bastion_drift_events` row with reason `exception_expired`. In the same transaction it writes outbox rows for `control.drifted` and the task upsert, using the existing reopen-to-start-phase rule and the comment "Accepted risk expired on {date}". When an exception is approved, comment on the task ("Risk accepted until {date}") instead of leaving it to the human. Add to §11.2: "exception approved, task closed, exception expires: task is open".

**Minor (design):**
- §2.1: say whether assertions on a control whose applicability is derived `not_applicable` stop being evaluated (as retired controls do) or keep producing snapshots that no view shows.
- §2.3: `population_review` and `not_assessed` both map to `confirm_check` at cost 1, so "Quick wins" will put 180-day re-confirmations above real failures. Consider cost 2 for `population_review`.

## Security

**Round-2 verification:** all three findings and all ten round-2 minors resolved in the section text. security-1 (both halves: migration `0261` adds the decider columns, `owning_app` and `require_human_decider`; the platform route returns 409 `DECIDE_IN_APP` for Bastion proposals; Bastion's two decide routes check `requireCan`, `rejectWhenImpersonating` and `kind === 'human'`, and the exception route requires approver != proposer; foreign decisions are ignored and recorded as `decision_rejected`; §11 covers it). security-2 resolved as specified (signed seal objects in the bucket, `epoch`, restores matched to a platform restore and acknowledged by an owner, unmatched gaps raise `evidence.integrity_failed`, lost ranges shown to the auditor), with the gap below. security-3 resolved (§2.6 `pass_with_exception` under Not met, questionnaire cap at `medium` naming the exception, approver != proposer, frozen refs, 90/365-day caps). Minors: definer probe functions hardened (§3.1); purge guarded by the age predicate with a test (§3.4); pre-org definer resolvers (§3.5); "evidence file missing" to auditors (§3.4); `pd_mismatch` on read (§3.4); redacted evidence stops counting (§3.3); every signing public key published (§3.4, §9.4); feed-key pepper env var (§3.5, §9.4); room Unlock (§5.2, row 87); policy body visibility re-checked per request (§3.6).

1. **[security] MAJOR - After a restore is detected, new ledger entries reuse sequence numbers that are already sealed, and the next day's seal makes the gap look normal.**
   - Where: §3.4 "Restore detection", steps 2-4. §4.1 `bastion_ledger_restores`.
   - Why it matters: **Pending window:** sequence numbers jump past the bucket seal (`seq` continues from `bucket_seal.head_seq + 1`) only after an owner acknowledges the restore. Until then "evaluation keeps running", so each new snapshot is written in epoch 1 at the next sequence number after the restored head. Those numbers are already covered by published signed seals, so auditors holding an older packet see two different signed chains for the same (epoch, seq). **Unmatched case:** an `unmatched` restore "cannot be acknowledged away", so the epoch never increments and the reuse never stops. **Detection resets itself:** the check compares against the newest seal object in the bucket, by date. The next nightly seal writes a newer object at the rewound head, so the following check returns "normal". The only remaining record is a mutable database row, `bastion_ledger_restores`. Someone who rewinds the ledger directly in the database, with no platform restore, only has to wait one seal cycle for detection to go quiet. **Tests won't catch it:** the restore integration test in §11.2 stops at detection.
   - Fix: On detection, whatever the restore's status, immediately open a provisional epoch and continue `seq` from the highest `head_seq` across all bucket seal objects, plus one. Acknowledgement only changes the label from "unexplained" to "restore", never the numbering. The seal run refuses to sign a head below the highest bucket-sealed `(epoch, head_seq)`. Write each lost range as a bucket object (`restores/<org>/<id>.json`) so it survives a database rewrite. Extend the §11.2 test: append after detection, seal again, and assert no sealed (epoch, seq) is reused and the gap is still reported the next day.

No blocker findings.

**Minor (security):**
- `POST /internal/bastion/proposals/:id/close` should accept only proposals with `owning_app = 'bastion'` and a decider who is a human member of that org. As written, any holder of the service credential can close any proposal under any decider name.
- The probe org guard needs `set_config('app.current_org_id', ...)` inside the read-replica transaction too; `runInOrgScope` binds only the primary, so every replica-routed probe would raise and show as `probe_error`.
- Bucket seal objects can be deleted with the S3 credentials every service shares. Within the stated honest limit, but worth one sentence in the guide telling auditors to keep their own copies of seals they receive.

R3-1. **[infrastructure] MAJOR - On Railway the worker never gets `BASTION_S3_BUCKET` or `BASTION_PD_HMAC_KEY`, so audit packets fail in production while passing locally.**
   - Where: §9.1 (worker env), §9.4 (worker `env.optional` and the hints), §7.2
   - Why it matters: The worker already exists on Railway. The scoped #126 fix only adds hints marked `propagate: true`, which is only the `*_API_INTERNAL_URL` and `*_API_URL` URLs. `BASTION_S3_BUCKET` is a `literal` without `propagate`, so it never reaches the worker, and the packet, sweep and mirror drivers are built with no bucket name. `BASTION_PD_HMAC_KEY` is a `secret`. `fillMissingSecrets` (`scripts/deploy/railway-auto-deploy.mjs`) only fills secrets for services being created, and its copy sources (`SECRET_SOURCE_SERVICES`: api, minio, livekit, ...) do not include bastion-api. So the worker either has no HMAC key, or has a hand-set value that must match bastion-api's freshly generated one byte for byte; every packet's commitment check would then fail or report `key_changed`. Compose shares one `.env` across services, so none of this shows up locally. env-hints is a flat, global map, so the same variable name cannot be a generated `secret` on bastion-api and a reference to bastion-api's value on the worker.
   - Fix: Remove the HMAC key from the worker. Have the packet job call a bastion-api internal route to verify commitments, so the key lives in one service. Mark `BASTION_S3_BUCKET` `propagate: true` (a non-secret literal, safe to propagate). Add an M1 gate: the `syncNew` dry-run plan shows `BASTION_S3_BUCKET` and `BASTION_API_INTERNAL_URL` being added to the worker. Add an M9 Railway smoke test: one packet built and downloaded on staging.

R3-2. **[infrastructure] MAJOR - Running the evidence mirror inside `backup-database.job.ts` means a Bastion mirror failure, or a very long first mirror, fails or stalls the platform database backup.**
   - Where: §9.7 ("runs as part of `backup-database.job.ts` before the backup records status"), §7 `bastion-object-backup` row
   - Why it matters: In `apps/worker/src/jobs/backup-database.job.ts`, everything between `pg_dump` and `UPDATE platform_backups SET status = 'completed'` sits in one `try`, and any throw marks the backup `failed` and rethrows. An off-site endpoint that is unreachable, has bad credentials or a throttled upload would therefore stop the whole platform's nightly database backup, including for operators who never use Bastion. The first mirror copies every historical object inline before the backup can report its status. The spec also contradicts itself: §7 says "event, triggered by", §9.7 says "runs as part of".
   - Fix: Record the database backup's success first, exactly as today. Then enqueue `bastion-object-backup` with `jobId = backup.id`, and have it write its cursor and status to a separate column such as `platform_backups.bastion_mirror_status/cursor`. A mirror failure never changes the backup's own status. Have the mirror job enforce a per-run byte or object budget with a resume cursor and progress lines. `ops.backup_fresh` keeps reading both values, so the "current" rule is unchanged.

- The §7 job table still calls the mirror "event, triggered by"; make it match §9.7 once R3-2 is settled.

## Stability

**Round-2 verification:** all seven fixed in the sections. A (§7.3 assertions may span slices; `lock_timeout` 3 s; `put` timeout 5 s; invariant 12 + 8 + 5 + 3 = 28 < 30 asserted in `test/time-budgets.test.ts`); B (resume in place, unique `(run, assertion)` on snapshots); C fixed as designed, but it only works if bastion-api restarts after the restore (finding 2); D (`bastion_object_intents`, sweep pauses during an open restore, `holder_count`); E (`ordering_key`, oldest row per key, comments by `external_id`, re-drive); F (leased permits from `admitLlmCall`, confirmed at `apps/api/src/routes/internal-llm.routes.ts:66`, heartbeats while waiting, SIGTERM drain); G (mirror inside the backup job, "current" defined, worker bucket variables, own driver).

1. **[stability] MAJOR - A run released back to `queued` has nothing that re-enqueues it, and while it sits there it blocks every future full run for the org.**
   - Where: §7 `bastion-run-reaper` (moves resumable runs back to `queued`), §7.3 (SIGTERM releases claims to `queued`), §7 tick (re-queues only `partial` nightly runs), §4.1 partial unique `(organization_id) WHERE status IN ('queued','running') AND scope = 'all'`, the `bursar-level.job.ts` drive loop (a 409 ends the attempt successfully).
   - How it fails: (1) A bastion-api pod dies mid-slice (OOM, crash, or SIGKILL). (2) Compose sets no `stop_grace_period` anywhere, so Docker kills after its default 10 s grace, well short of "let the current LLM call finish" (up to 60 s). (3) The worker's retries hit the still-held claim and get 409, which the loop treats as "ends the attempt", so the BullMQ job completes. (4) Five minutes later the reaper sets the run to `queued`. Nobody enqueues it: the tick only re-queues `partial` rows; the BullMQ job has already finished; re-adding the same `jobId` is silently dropped while the completed job is still retained by `removeOnComplete`. (5) The orphaned `queued` row satisfies the partial unique index, so tomorrow's nightly insert, every manual full run and the agent tool are all rejected. Every control goes `evaluation_stale` 36 h later, and it never recovers without an operator.
   - Fix: Make the reaper, or a tick pass, re-enqueue every `queued` run whose `updated_at` is more than 2 minutes old. Always increment `resume_count` on release and use `jobId = run.id + ':' + resume_count`, so the add is never deduplicated against a retained job. In the drive loop, a 409 against a claim whose `heartbeat_at` is stale should delay and retry, not end the attempt. Set `stop_grace_period: 75s` on bastion-api in compose, and use the Railway equivalent. Add a test: kill the pod mid-slice, then assert the run completes and the next night's run is created.

2. **[stability] MAJOR - Restore detection compares sequence numbers only and runs only at boot and at 23:55. A platform restore taken from the Backup app while the stack is running is not detected, sealed sequence numbers get reused, and the result reads as "normal".** (Same family as security-1 this round.)
   - Where: §3.4 Restore detection (step 1: "head at or after the bucket seal: normal"; step 2: "evaluation keeps running"; checks happen "at boot and in each seal run"). `restore-database` is an in-app worker job enqueued by the api after a SuperUser confirmation (`apps/worker/src/worker.ts:2676-2706`), so bastion-api is not restarted.
   - How it fails: The database is restored to last week. bastion-api keeps running, so the boot check never fires. The evaluator appends about 150 entries per night, starting at the restored head, so it reuses sequence numbers that were already sealed and published with different hashes. By 23:55 the head may be at or past `bucket_seal.head_seq`; step 1 then says "normal", and no `bastion_ledger_restores` row is ever opened. An auditor holding the old seal or packet now sees sequence X with a different hash, and nothing explains it. Even when detection does fire, step 2 lets evaluation keep appending inside the lost range until the owner acknowledges, which breaks "a sealed seq is never reused".
   - Fix: Compare identity, not position: the database entry at `bucket_seal.head_seq` must exist and its `entry_hash` must equal the bucket seal's `head_hash`; anything else opens a restore row. Run the check at the start of every ledger-append transaction batch, cheaply (cache the verified seal per org, and recheck when `max(platform_restores.completed_at)` changes). While a restore row is open, block ledger appends for that org; the run goes `partial` with reason `restore_pending`, which the existing resume logic handles. Add an integration test with no restart: seal, append, restore the dump in place, run an evaluation, and assert a restore row exists with no sequence reused.

**Minor (stability):**
- §3.4 lists `bastion_evidence_objects` under four-path immutability, but `holder_count`, `mirrored_at` and `bytes_redacted_at` are updated in normal operation. Name exactly which columns the `WHEN` clause covers.
- §7 does not say whether a `dead` outbox row keeps blocking its `ordering_key`. State it.
- Compile and autofill now run 1-2 hours and 16-32 minutes (§7.3). A copied `MAX_POLLS = 200` with a few-second poll interval runs out first; specify the poll interval and the cap against those durations.
- The first mirror pass may copy every existing object; state that a mirror failure or timeout never fails the database backup itself, and give the pass a per-run object budget. (Same as infrastructure R3-2.)
- The seal object is written asynchronously through the outbox. If the database is restored before the outbox delivers it, detection works against the older seal but reports a wider lost range. Note this as expected behavior.

## Best practices

**Round-2 verification:** bp-1 fixed (§8.1 `enqueueBastionEvent` with literal names, the catalog check reads that helper, a test asserts `BASTION_EVENT_TYPES` equals `bastionEvents`, registration at M4); bp-2 fixed (`db-drift.yml` step comparing the live enum with `BOLT_SOURCES`); bp-3 fixed (`<generate>`, `stable: true`, notes, 64-hex Ed25519 seed, `signing_key_id` rotation); **bp-4 partly open** (the M11 merge unit is right, but M10's "built and tested (not registered)" fails two gates that count files, finding 3); bp-5 fixed in §3.1, but the GRANT target is a problem (finding 1).

1. **[best-practices] BLOCKER - `0268`'s "GRANT EXECUTE ... TO the app role" grants to a role that does not exist.**
   - Where: §3.1 (the REVOKE and GRANT step), §4.4 `0268`.
   - Why it matters: no migration, compose file, `.env.example` or deploy script creates an app role. The only name in code is `bam_app`, the default in `apps/api/src/boot/rls-boot.ts`, which only logs a warning when the role is missing. Every service connects as `POSTGRES_USER`, and that same user owns the functions. A builder who writes `GRANT ... TO bam_app` gets `role "bam_app" does not exist`, and `0268` aborts on every fresh database. Because `migrate` is a `service_completed_successfully` dependency, that takes down the whole local stack. On Railway it blocks every later migration, which is the 0124 incident pattern.
   - Fix: Name the grantee exactly. Wrap the GRANT in `DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'bam_app') THEN GRANT EXECUTE ... TO bam_app; END IF; END $$;`, or grant to `current_user`. Write the `proacl` assertion to accept an owner-only ACL; today the owner is the connecting superuser, so REVOKE plus owner execute is the real posture.

2. **[best-practices] MAJOR - The org guard will raise on every probe that runs on the read connection, and on Railway that connection is always used.** (Same as a security minor this round.)
   - Where: §3.1 (the guard "raises unless `org = current_setting('app.current_org_id', true)`"; probes run "On `DATABASE_READ_URL`"), §9.5.
   - Why it matters: `runInOrgScope` sets the GUC with `set_config(..., true)` on the primary pool only (`apps/bursar-api/src/plugins/rls.ts:65`). A `READ ONLY` transaction opened on the read pool has no GUC, so every probe raises, records `probe_error`, and after two nights every native control reads "Can't prove yet". The Railway hint sets `DATABASE_READ_URL` to the primary's URL (`env-hints.mjs:90-94`), so production always takes the read path. On a primary, `pg_last_xact_replay_timestamp()` returns NULL, so the replica-lag comparison is undefined.
   - Fix: Add `runInOrgScopeRead(orgId, fn)` that runs `BEGIN READ ONLY`, `set_config('app.current_org_id', org, true)` and `SET LOCAL statement_timeout` on the read pool. Treat a NULL replay timestamp as zero lag. Run the probe goldens a third time with `DATABASE_READ_URL` pointing at a separate pool.

3. **[best-practices] MAJOR - "MCP tools built and tested (not registered)" at M10 turns two CI gates red until M11.**
   - Where: §12 M10, against the §9.6 M11 merge unit.
   - Why it matters: `scripts/check-tool-return-coverage.mjs` counts `registerTool(server, {` in every `apps/mcp-server/src/tools/*-tools.ts` file on disk; it does not look at `server.ts`. With `bastion-tools.ts` committed at M10 the count is 909 while every published number says 885, so the `db-drift.yml` tool-return-coverage job fails. `listAllToolModules()` (`tool-source.mjs:397-403`) also reads the directory. With no `APP_TOOL_MODULES` entry yet, `bastion-tools` is filed under "platform", so `pnpm docs:catalog:check` reports the committed JSON as stale and lint fails.
   - Fix: `bastion-tools.ts` is created only in the M11 merge unit. At M10, build and test the client and the tool handlers under a path that does not match `*-tools.ts`, for example `apps/mcp-server/src/clients/bastion-client.ts` plus `src/tools-pending/bastion.ts`. Alternatively, fold all MCP work into M11.
