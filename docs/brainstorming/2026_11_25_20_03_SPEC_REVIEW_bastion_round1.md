# Bastion spec review - round 1

Spec under review: `docs/brainstorming/2026_11_25_20_03_APP_DESIGN_bastion.md` (draft at 5f95f37c). Five adversarial reviewers, one per focus. Findings are verbatim.

## Design

1. **[design] BLOCKER - The flagship "can't prove yet" ranking is missing cases, and on day one it fills up with setup work instead of real gaps.**
   - Where: section 2.3 (severity table), section 3.2 (reason codes), section 4.1 `bastion_gaps.gap_kind`, section 6.1 Readiness page
   - Why it matters: `gap_kind` has 7 values, but the severity formula only scores 5 of them. `manual_missing` and `not_yet_confirmed` have no severity at all. Two `unprovable` reasons (`insufficient_data`, `probe_error`) have no gap kind. The "self-attested, lower severity relief" weighting (section 3.3 table) is never turned into a number. A `mixed` control has no defined place in the four home numbers ("Proven by the suite" or "Proven by evidence you provided"?). On top of that, adopting SOC 2 leaves every control `unprovable/not_yet_confirmed` until a human confirms it. So the first ranked list a non-technical owner sees is 60+ "Nobody has confirmed how to check this yet" rows, and "Can't prove yet" reads close to 100%. The flagship output is wrong exactly when the first impression is formed. Implementers will each invent their own mapping.
   - Fix: Add one authoritative table mapping each `(status, reason) -> gap_kind -> severity -> default fix_template`. It must cover all 7 reasons, plus `attestation_statement`-only coverage (a relief factor, e.g. severity x 0.6). Keep `not_yet_confirmed` out of the gap list and out of the four numbers. Show it as a separate "Setup: N of M controls have a confirmed check" progress bar on Readiness and in the setup wizard. Define `mixed` as counting toward "Proven by evidence you provided" if any passing assertion is manual or attested, so the suite number never overstates. Have `BASTION_SEED_EXPECTATIONS` assert the mapping.

2. **[design] MAJOR - The `change.merge_reviewed` precondition reports a team that never reviews code as "not connected" instead of "Not met", then drafts the wrong fix.**
   - Where: section 3.1 probe table (`change.merge_reviewed` precondition: "at least one review event received in 30 days"), section 15.6
   - Why it matters: Take a team that merges 40 PRs with zero reviews, which is the worst real case. It produces no `pull_request_review` events, so the precondition fails and the control is `unprovable/source_not_connected`. The drafted fix is then "tick Pull request reviews in your webhook". The product hides the most important change-management failure behind a setup instruction. That breaks the spec's own rule that Bastion never claims more than it can prove.
   - Fix: Detect whether review events are subscribed from the webhook configuration, not from whether reviews happened. GitHub's `ping` delivery carries `hook.events`, and `apps/api/src/routes/github-webhook.routes.ts:137-138` already receives `ping` and discards it. Store the subscribed event list on `github_integrations` (e.g. `subscribed_events text[]`, an additive migration), or record the most recent `pull_request_review` subscription seen. The precondition becomes "the integration is subscribed to `pull_request_review`". Merges with no approval then yield `fail`. Apply the same audit to every precondition: no precondition may be satisfiable only by the control actually operating.

3. **[design] MAJOR - Probes check only the systems someone connected, so partial coverage passes as 100%.**
   - Where: section 3.1 (`change.merge_reviewed`, `change.merge_traceable`, `logging.retention_floor`, `automation.failure_rate`), section 6.2
   - Why it matters: `github_integrations` allows one repo per project (`project_id ... .unique()`, `apps/api/src/db/schema/github-integrations.ts:19-22`). An org with six repos that integrated one gets "100% of merges reviewed" and **Proven**. Likewise, logging retention covers only Blip tracked apps. Auditors test completeness of the population first (the "information produced by the entity" question), so a control proven on an unstated subset fails audit and destroys trust in every other green.
   - Fix: Give each population-based probe a human-confirmed `expected_population` parameter in `paramsSchema`, e.g. the list of in-scope repos. The compiler proposes it from what it finds and the human confirms it, using the existing confirm gate. Any expected member that is not connected yields `unprovable/source_not_connected` naming the repo. Every `explain()` and snapshot `summary` must state the population checked ("1 repository checked: Rescue Radio Firmware"). Add a probe-golden test where one expected repo is missing.

4. **[design] MAJOR - There is no exception or risk-acceptance object, so a past or justified violation keeps a control "Not met" with no legitimate way to resolve it.**
   - Where: section 2.3, section 2.5, section 3.2, section 4.1 (only `bastion_gaps.status = dismissed`), section 7.2 packet
   - Why it matters: A rolling 30-day window means one unreviewed hotfix (PR #42 in the seed) holds the control at `fail` for 30 days after a post-merge review has fixed it. A deliberately long-lived service key with a compensating control fails `keys.max_age` forever. Dismissing the gap does not change the control status, the four numbers, the questionnaire banding (which forces `low`), or the trust-page publish block. Teams will then loosen thresholds just to get green, which is worse than recording the exception. Auditors expect an "exceptions noted, with management response" record. The packet has only `drift.csv`.
   - Fix: Add `bastion_exceptions` with these columns: `id`, `organization_id`, `control_id`, `assertion_id`, `cited_ref` (one entity), `reason`, `compensating_note`, `approved_by`, `approved_at`, `expires_at NOT NULL`, `ledger_seq`. It is immutable and ledgered, and gets a new `exception` `entry_kind`. Approval runs through `agent_proposals`, so agents can propose and a floored human decides. Snapshots keep the raw `fail`. Control status becomes `pass` with a visible "1 accepted exception" marker. Add `exceptions.csv` to the packet and show exceptions in the auditor room. Add the corresponding permission row(s) to section 5.5.

5. **[design] MAJOR - Adopting two frameworks duplicates every control, assertion, evidence link, and remediation task, and the home screen does not say which framework its numbers describe.**
   - Where: section 2.1 ("Adopting a template copies its controls into org rows"), section 4.1 `bastion_controls` unique `(organization_id, framework_id, ref_code)`, section 2.5 `external_id = 'bastion:control:<control_id>'`, section 6.1 Readiness
   - Why it matters: The section 1.2 customer (SOC 2 now, then a buyer asking for ISO 27001) adopts both. The same MFA report must then be uploaded or linked and reviewed twice. One drift produces two Bam tasks, because `external_id` is keyed per framework control. Questionnaire retrieval returns near-duplicate controls, and the four numbers mix both frameworks. "Test once, comply many" is the core GRC value a small team cannot afford to lose.
   - Fix: Either (a) limit v1 to one active framework per org with a partial unique index on `bastion_frameworks (organization_id) WHERE status='active'`, and record multi-framework as v1.1, or (b) make controls org-level and add `bastion_control_requirements(control_id, framework_id, ref_code)` mapping one internal control to many framework requirements. Option (b) keeps assertions, evidence, gaps, and tasks single, and makes the four numbers filterable per framework. Recommend (b). The template library already carries `ref_code` per control, so ship a static SOC 2 to ISO 27001 crosswalk in `library/` code.

6. **[design] MAJOR - The one-task-per-control upsert silently updates a task a human already closed, so repeat drift becomes invisible.**
   - Where: section 2.5, section 8.4 (`internal-bastion.routes.ts` keyed on the 0130 `(project_id, external_id)` index)
   - Why it matters: `apps/api/src/services/task-upsert.service.ts:200-256` does `onConflictDoUpdate`. It only changes `phase_id`/`state_id` when the caller passes them, so a task in the Done phase stays Done. The scenario: control fails, a human fixes it and closes the task, and Bastion only comments on recovery. When the control fails again a month later, the update lands on a closed task nobody looks at. That defeats the spec's stated retention mechanism ("drift that produces no task is the problem the product exists to solve"). Also, when `compliance_project_id` is unset, no task is created at all, and nothing tells the user.
   - Fix: Specify reopen semantics in the internal route. If the existing task is in a terminal phase or state, either move it to the project's first phase and add a "Drifted again on {date}" comment, or start a new cycle with `external_id = 'bastion:control:<id>:<drift_event_id>'` and link the previous one. Pick one and add it to the section 11.2 cross-app flow ("drift, close, drift again: the task is open"). Make choosing or creating the compliance project a required setup-wizard step (offer **Create a "Compliance" project for me**). Readiness should show a banner while it is unset.

7. **[design] MAJOR - Policy attestation does not check that the required people can actually read the Beacon article they are asked to attest to.**
   - Where: section 3.6, section 6.1 `/bastion/attest`, section 5.5 (viewers get `attestation.sign`)
   - Why it matters: The SPA fetches the body from beacon-api under the member's own session. Beacon entries are project-scoped (`idx_beacon_entries_org_project_status`, `apps/beacon-api/src/db/schema/beacon-entries.ts:81`), so a viewer or a member outside that project gets a 403. That person either cannot attest, which leaves `policy.attested` "Not met" forever with no clear reason, or the UI lets them attest to text they never saw, which is invalid evidence. Separately, Beacon entries carry a mandatory `expires_at` (line 61), and the `beacon-expiry-sweep` can retire a policy article underneath Bastion.
   - Fix: When a policy is linked, and nightly, run `can_access(member, 'beacon.entry', id)` for every audience member. Unreadable members become a distinct `policy.attested` cited ref ("3 people can't open this policy") with a `config_change` fix ("share the article with everyone"). Alternatively, serve the frozen `beacon_versions.body_markdown` that Bastion already reads server-side for hashing through a bastion-api read route, so what is shown and what is hashed are guaranteed to be the same bytes. Recommend the second option for evidentiary integrity. Have `policy.current` cite Beacon's own `expires_at` so expiry shows up as a gap before the sweep fires.

8. **[design] MAJOR - The v1 scope is too broad for the wedge: 28 tables, 91 routes, 14 jobs, plus a public trust page and custom-document framework extraction.**
   - Where: section 1.2 wedge, section 5.2 trust page, section 2.1 steps 3-4 (custom frameworks), section 12 M6-M8
   - Why it matters: The vote (brainstorming session Phase 5) was won on the ranked "can't prove yet" list plus native evidence. The trust page is a public marketing claim surface. It brings its own publish gate, a slug namespace, a second public route, and legal exposure (section 14.1 already needs a disclaimer footer). It overlaps the auditor room for the small-firm customer. Custom-framework LLM extraction is the only compile path that needs the LLM, and the only one needing `verifyCite` corpus gates. Both push the wedge-bearing milestones (M5 gaps, M7 questionnaires) later, and they add the highest-liability surfaces to a first release.
   - Fix: Move the trust page (rows 76-79, 89, `bastion_trust_pages`, `trust_page.*` permissions, Playwright 7) and custom-document frameworks (M6 extraction, the 12-control corpus) to v1.1 in section 14. Keep built-in templates with LLM tailoring plus the deterministic fallback. Recount the section 5.5 table and the section 4.6 sanity line in the same change. Use the freed capacity on the exceptions and population items above.

9. **[design] MINOR - Machine feeds require an owner or admin `bbam_` API key in a cron script, a high-privilege credential for a write-only job.**
   - Where: section 3.5 ("authenticated by a normal `bbam_` API key whose user holds `bastion.feed.write`"), section 5.5 (`feed.write` floored)
   - Why it matters: An HR or MDM export script then holds a key that can also confirm assertions, review evidence, create auditor rooms, and act in every other app. A non-technical operator will not know to mint a narrowly scoped service account. A leaked key also defeats the ledger's purpose, because the same key can push fabricated feed records and accept them.
   - Fix: Reuse Blip's per-target ingest credential pattern (`apps/blip-api/src/db/schema/blip-ingest-keys.ts`). Add `bastion_feed_keys`: one token per feed, shown once, only an HMAC stored, `last4`, individually revocable, and allowed only to append to that one feed. Create it from the feed's settings page with a plain **Create a key for this feed** button. Record `feed_key_id` on each `bastion_feed_records` row, so an auditor can see which credential pushed each record.

Files the design reviewer checked: `apps/api/src/services/task-upsert.service.ts`, `apps/api/src/db/schema/github-integrations.ts`, `apps/api/src/routes/github-webhook.routes.ts`, `apps/api/src/db/schema/agent-proposals.ts`, `apps/beacon-api/src/db/schema/beacon-entries.ts`, `apps/beacon-api/src/db/schema/beacon-versions.ts`, `apps/blip-api/src/db/schema/blip-ingest-keys.ts`, the session doc. The section 5.5 permission table was confirmed internally consistent (47 actions, 24 floored, member 23, viewer 9).

## Stability

1. **[stability] BLOCKER - The evaluator's slice size, probe timeout, engine HTTP timeout and run lease contradict each other, so nightly runs will get reaped and retried over and over.**
   - Where: §7 (`bastion-evaluate-tick`: 25 assertions per slice, re-enqueue until done), §2.8 (`statement_timeout = 15s`), §9.1 (`BASTION_ENGINE_TIMEOUT_MS=30000`), §7 `bastion-run-reaper` (5-minute lease), §9.5.
   - Why it matters: one slice can legitimately take 25 x 15 s = 375 s. The worker's `postBastion` (a copy of `apps/worker/src/jobs/bursar-shared.ts`) aborts its fetch at 30 s, but bastion-api keeps running the slice. BullMQ then retries (Bursar's opts are `attempts: 5`, exponential backoff, `worker.ts:2563-2568`) and gets 409s against its own still-running slice. The slice also outlives the 5-minute lease, so the reaper flips the run to `partial` while it is still writing snapshots. The spec also never says whether one tick job drives every org's slices inline. `registerBursarSweep` runs with `concurrency: 1`, so 41 orgs x 6 slices run one after another inside a single 15-minute tick, and later ticks queue up behind it.
   - Fix: Size each slice by a time budget, not a fixed count. Stop taking new assertions when elapsed time reaches 20 s, keep the probe timeout at 15 s or less, and heartbeat after every probe, not every slice. Split the tick from the work. The tick only claims due runs and enqueues them on a separate `bastion-evaluate-run` queue with `jobId = run.id` (BullMQ dedups on it), a bounded concurrency, and the drive loop from `apps/worker/src/jobs/bursar-level.job.ts` (MAX_POLLS cap, 409 ends the attempt, 429 throws). Add a unit test asserting slice budget < engine timeout < lease. Use the same budget rule for compile (10 controls with an LLM call each) and autofill (20 rows x `BASTION_LLM_TIMEOUT_MS=60000` = 1,200 s per slice, which breaks the same way).

2. **[stability] BLOCKER - Nothing marks evidence as stale, and infrastructure failures read as compliance failures. A dead evaluator leaves "Proven" on screen indefinitely, and a flaky dependency floods the org with drift.**
   - Where: §2.2, §2.5, §3.2 (`probe_error`), §3.4 (object written before the transaction), §6.1 Readiness, §5.2 trust page publish gate.
   - Why it matters: if the worker, Redis or the tick stops, `bastion_controls.status` stays at its last value. The home page, trust-page gate, questionnaire banding and auditor room then keep calling a control **Proven** with no limit on how old the result is. That is the worst possible failure for a compliance product. In the other direction, a statement timeout, a read-replica blip or MinIO being down produces `pass -> unprovable(probe_error)`. Under §2.5 that counts as worsening, so it writes a drift event, publishes `control.drifted`, upserts a Bam task, then comments `control.recovered` the next night. That cycle repeats every time infrastructure hiccups. The spec also never says what outcome results when the MinIO object write fails before the ledger transaction.
   - Fix: Add a staleness rule: a control whose `last_evaluated_at` is older than 36 h (configurable) displays and computes as `unprovable / evaluation_stale` everywhere status is consumed (home, gaps, trust-page publish, questionnaire banding, auditor room). Treat infrastructure failures (`probe_error`, storage write failure, read-only transaction failure) as non-drifting: keep the previous status, set a `stale_reason`, and require 2 consecutive `probe_error` nights before treating it as drift. If MinIO is unavailable, end the slice without writing a snapshot or ledger row, and finish the run as `partial` with reason `storage_unavailable` instead of per-control failures. Add a `bastion-evaluation-missed` check that records a worker error through `recordWorkerError` when no nightly run completed for an org in 26 h.

3. **[stability] MAJOR - Control status has several uncoordinated writers, and status is aggregated per slice rather than per control. The result is transient drift and last-write-wins regressions.**
   - Where: §2.2 (worst of assertions), §4.1 `bastion_evaluation_runs` (partial unique only `WHERE status='running' AND scope='all'`), §7 (`bastion-evidence-expiry` "re-evaluates affected manual assertions"), row 18 control-scope runs, §3.3 review acceptance.
   - Why it matters: Fixed 25-assertion slices split a control's assertions across slices. If status is written per slice, a half-evaluated control flips status and fires `control.drifted` mid-run. A reaped `partial` run leaves controls aggregated from incomplete data. The nightly slice, a control-scope run (no uniqueness and no rate limit; only full runs are limited), the expiry job and review acceptance all write `bastion_controls.status`. A slice that started before an expiry flip can commit after it and overwrite the fresher result. Two concurrent control-scope runs both detect the same transition, which doubles the drift events and Bolt events. "No nightly run today" has no unique key, so a retried tick or a manual run in the same hour can produce two nightly runs.
   - Fix: Partition slices by control, never by raw assertion count. Aggregate and write status only after every confirmed assertion of that control has a snapshot in this run. Make the status write conditional: `UPDATE ... SET status=..., last_evaluated_at=$as_of WHERE id=$c AND (last_evaluated_at IS NULL OR last_evaluated_at < $as_of)`. Emit drift only when that update changes the row (`RETURNING` the old status). Add a partial unique index on `(organization_id, control_id) WHERE status='running' AND scope='control'`. Add `nightly_for_date date` with a unique index on `(organization_id, nightly_for_date) WHERE trigger='nightly'`. Every probe reads `run.as_of`, never `now()`.

4. **[stability] MAJOR - The retention job contradicts the immutability triggers, and evidence growth has no limit or plan.**
   - Where: §3.4 (four-path immutability on `bastion_auditor_access_log`, `bastion_feed_records`), §7 `bastion-retention` ("prunes ... auditor access logs older than ..."), §3.4 "orphaned object ... swept", §3.5 feed push, §4.4 "no partitioning".
   - Why it matters: `bastion-retention` issues a DELETE against a table whose BEFORE DELETE trigger raises (the same function shape as `0249_bursar_awards_baseline.sql:116-131`). The daily job fails permanently and fills `removeOnFail`. The orphan-object sweep appears in no job table. Written naively (list `<org>/bastion/objects/`, delete keys missing from `bastion_evidence_objects`), it races a transaction that has `put` the object but not yet committed, and deletes bytes of committed evidence. The 55k rows per org per year sizing covers snapshots only. `bastion_feed_records` takes 500-record batches with no quota, each row up to 16 KB of jsonb plus a ledger row, and DELETE and TRUNCATE are both refused. One looping HR script creates permanent, undeletable bloat.
   - Fix: Drop access-log pruning, or exempt that table from the DELETE trigger and protect it through the ledger instead. Pick one and state it. Specify `bastion-object-sweep` with a minimum object age of 24 h, `stat` before delete, a re-check of the DB row inside the loop, and progress logging. Add a per-feed daily record quota (in `bastion_evidence_feeds`, 429 when exceeded) and per-org feed storage accounting. State that `bastion_feed_records` and `bastion_ledger_entries` are the high-volume tables, and record the row count at which monthly `created_at` partitioning becomes mandatory (the activity-log precedent).

5. **[stability] MAJOR - The manual-evidence pipeline only accepts `scan_status = 'clean'`, so it never completes on many real installs.**
   - Where: §3.3 steps 1-3, §7 `bastion-evidence-ingest` (`*/10` retry).
   - Why it matters: `apps/worker/src/jobs/bin-av-scan.job.ts:13-23` also produces `skipped` (`BIN_AV_SCAN_MODE=off`), `error` (clamd unreachable, terminal until an operator acts) and `infected`. Bin serves `skipped` assets. With the Bursar four-check (`apps/bursar-api/src/lib/bin-asset-access.ts:78`, `!== 'clean'` throws), every upload on an AV-off install sits in `pending_scan` forever and is retried every 10 minutes forever. The flagship MFA evidence never activates, and the user sees nothing. `scan_status` is also per asset, not per version. If the user uploads a new Bin version after attaching, the asset goes back to `pending`, and the pinned (already clean) version is blocked until the new version's scan finishes.
   - Fix: Map every state explicitly: `infected` -> `blocked`; `error` -> `blocked` with reason `scan_failed` and a plain UI message; `skipped` -> allowed and labelled "Not virus-scanned (scanning is off)", or a stated policy decision to refuse. Cap `pending_scan` age (for example 24 h); after that, surface it in the review queue and stop retrying. Have the ingest job work through rows with `attempts` and `next_attempt_at` (the `bastion_ingest_events` shape) instead of an unbounded rescan. Copy the bytes once at attach time if the pinned version is already clean, so later version churn cannot block it.

6. **[stability] MAJOR - Side effects that leave the transaction (Bam task upsert and comment, Bolt events, the daily `ledger.sealed` witness) have no outbox and no retry. One of them can hang a job indefinitely.**
   - Where: §2.5, §3.4 External witness, §7 `bastion-ledger-seal`, §8.4 `internal-bastion.routes.ts`.
   - Why it matters: `publishBoltEvent` (`packages/shared/src/bolt-events.ts:35-65`) is fire-and-forget, catches every error, and passes **no AbortSignal or timeout**. If bolt-api is down at 23:55 UTC, that day's seal is lost silently, which leaves a hole in the tamper-evidence story. If bolt-api hangs, the seal loop or evaluator slice hangs until the lease reaps it. If api is down during drift, the drift row exists with `bam_task_id = null` and nothing retries the task. `bastion-proposal-reconcile` only covers proposals. The recovery comment is not idempotent, so a BullMQ retry posts duplicate comments.
   - Fix: Add a `bastion_outbox` table (or reuse the `bastion_ingest_events` claim, heartbeat and attempts shape) written in the same transaction as the drift, seal or evidence row. A drainer job delivers it with backoff, and an idempotency key (`drift_event.id`) is sent to `/internal/bastion/tasks/:id/comment`, which dedups on it. Persist each day's seal in a `bastion_ledger_seals` row with a `published_at` column, and retry until it is set. Wrap Bastion's publish calls in a timeout (pass an `AbortSignal.timeout(5000)` helper, or fix it in `bolt-events.ts` for every app and record that as a pre-existing defect).

7. **[stability] MAJOR - Ledger hashing has no fixed canonical form, so it can raise false `evidence.integrity_failed` alarms, and verification is unbounded at request time.**
   - Where: §3.4 (`entry_hash = sha256(... || recorded_at_iso)`, `GET /evidence/:id/verify` "walks the ledger from the entry to the current head", weekly verify "plus everything an open auditor room references").
   - Why it matters: `timestamptz` keeps microseconds, but JS `Date.toISOString()` keeps milliseconds and always renders UTC with a `Z` suffix. If `recorded_at` comes from a DB default `now()`, or is re-rendered in a session timezone, the verifier recomputes a different string. A false "evidence tampered" event in front of an auditor is worse than no check at all. Walking from a year-old entry to the head is about 55k+ rows hashed synchronously inside a 120 req/min public-capable route. An open room covering all controls for a year makes the weekly verify stream every referenced object from MinIO, with no limit.
   - Fix: Specify a canonicalizer used by both writer and verifier: `recorded_at` set in the app and truncated to milliseconds, UTC `Z` ISO, fields joined with a length-prefixed or explicit delimiter (plain `||` concatenation is ambiguous), `seq` included, and the hex and case of `prev_entry_hash` fixed. Add a golden test that round-trips a row through Postgres. Bound request-time verify to "entry -> next sealed checkpoint" using the persisted seal rows from the previous finding. Give the weekly job a per-run object budget with resume and progress logging.

8. **[stability] MAJOR - The audit packet build has no defined home and no memory limit.**
   - Where: §7 `bastion-export-packet`, §7.2 (`jszip`, `pdf-lib`, "worker deps"), §5.1 row 73 (202 + run), §7 header ("engine logic lives inside bastion-api").
   - Why it matters: the spec says engines run in bastion-api behind a 30 s engine call, but cites worker dependencies for the packet. A one-year SOC 2 Type II packet contains about 55k snapshot JSONs plus pen-test PDFs and other manual files. A default `jszip.generateAsync` buffers the whole archive in memory, and `summary.pdf` (one page per control with full history) is built in memory too. That risks an OOM kill of bastion-api or the worker and takes other jobs down with it. It also cannot be split into slices the way §7 implies.
   - Fix: Decide that it runs in the worker as a single long job with its own lease and heartbeat, not through the 30 s engine route. Stream it: `generateNodeStream({ streamFiles: true })` piped into `@bigbluebam/storage` `put(key, stream)` (`packages/storage/src/driver.ts` accepts a ReadableStream). Write each content-addressed object once and reference it from the manifest instead of once per snapshot. Cap packet size and period (reject anything over N GB with a plain error), and checkpoint stage progress to the `bastion_export_packets` row per §7.1.

9. **[stability] MINOR - Clock and timezone rules are underspecified for "today", expiry and the cron schedules.**
   - Where: §7 schedule table, §4.1 `bastion_org_settings.timezone` / `evaluation_hour_local`, §3.3 `valid_until >= now`, §6.2.
   - Why it matters: `upsertJobScheduler` patterns fire in the worker process's local timezone unless `tz` is passed (`worker.ts:2624` passes none). The schedules only line up with "UTC" if the container TZ happens to be UTC. "No nightly run today" is ambiguous across a DST change (hour 2 local is skipped or repeated) and across an org timezone edit. If `valid_until` is a `date`, comparing it to `now()` makes evidence expire at UTC midnight. The 06:10 UTC expiry job, the 03:00-local evaluator and the "expires in 12 days" UI text then disagree by up to a day. The scheduler and its retention live in the copied helper. New event-driven producers in bastion-api (compile, autofill, ingest, export) do not inherit `SCHEDULED_JOB_RETENTION` (`apps/worker/src/lib/job-retention.ts`).
   - Fix: Pass `tz: 'UTC'` explicitly on every scheduler. Compute `nightly_for_date` as `(now() AT TIME ZONE org.tz)::date` at claim time, and resolve DST by "first tick at or after the local hour". Define `valid_until` as an end-of-day instant in the org's timezone, computed by one shared helper used by the evaluator, the expiry job and the SPA. Require every producer `Queue.add` in bastion-api to pass `jobId = <run id>` plus `SCHEDULED_JOB_RETENTION`, and require every scheduler to go through `withRetention`. Add a unit test that scans for bare `upsertJobScheduler` calls.

## Security

1. **[security] BLOCKER - Any signed-in user can download restricted evidence through the platform's shared file route.**
   - Where: §3.3 step 3 (key `<org>/bastion/objects/<sha256>`), §3.4 snapshot dedup, §6.2 "Technical details" (shows the hash), §5.2 ("files stream through bastion-api").
   - Why it matters: `apps/api/src/routes/upload.routes.ts:187-222` serves any key in `env.S3_BUCKET` behind only `requireAuth` plus `shadowOnly('bam.file.list')`. It does not check the org or the key prefix, and it sends `Cache-Control: public`. That is the same `bigbluebam-uploads` bucket Bastion writes to (`apps/api/src/env.ts:60`, `apps/bin-api/src/env.ts:36`). The key is just the org id plus the content hash, and the spec shows that hash to every `evidence.read` holder, which includes viewers. So any viewer can fetch `/files/<org>/bastion/objects/<sha>` and get restricted HR or pen-test files with no `read_restricted` or room check. Members of other orgs can too, once they learn the org id and a hash. "Streams through bastion-api so every download is logged" is false while this route exists.
   - Fix: Fix the cause, not just Bastion's copy. Restrict `/files/*` to the `avatars/` prefix it was built for (file as a pre-existing defect; Blip and Bin org-prefixed keys have the same exposure). Store Bastion objects under a prefix keyed by an HMAC of the content hash with a server secret, or under a random id with the hash kept only as a column, and never show `object_key`. Add a negative test: a GET of a Bastion key through `/files/` returns 404.
   - Orchestrator: confirmed and filed as issue #123.

2. **[security] BLOCKER - Probes become false "Proven" results once RLS enforcement is switched on.**
   - Where: §3.1 (`access.departed_still_holding`, `access.dormant_accounts`, `keys.*`), §2.8 ("probes run ... inside `runInOrgScope`"), §4.3.
   - Why it matters: `0116_rls_foundation.sql:97-104` lets `sessions` rows through only for users who still have an `organization_memberships` row in the current org. The user-deletion service removes memberships (`apps/api/src/services/user-deletion.service.ts:244`). Under `BBB_RLS_ENFORCE=1`, inside `runInOrgScope`, a departed user's live sessions are invisible, so `departed_still_holding` reports zero and passes. That is exactly the control it exists to catch. Any probe whose source table gains an RLS policy later fails the same way: "0 violations" is indistinguishable from "0 rows visible". This is the probe-side twin of issue #105.
   - Fix: Run probes through a reviewed `SECURITY DEFINER` read function or a dedicated BYPASSRLS read-only role. Do not use the org-scoped transaction for platform tables; keep the explicit org predicate. Give every probe a "can I see enough rows" precondition (for example, it must see at least as many members as `organizations` reports), otherwise the result is `unprovable/probe_error`. Run the §11.2 probe goldens a second time with `BBB_RLS_ENFORCE=1`.

3. **[security] MAJOR - A SuperUser impersonating someone can attest, accept evidence and approve answers in that person's name.**
   - Where: §3.6, §2.7 ("server rejects `users.kind <> 'human'`"), §3.3 uploader statement and reviewer acceptance, §5.1 rows 14, 31, 53, 62.
   - Why it matters: The auth plugin Bastion copies swaps `request.user` for the target when `X-Impersonate-User` is sent (`apps/bursar-api/src/plugins/auth.ts:308-353`). The target is a human, so the `kind` check passes. Attestations and acceptances are written to an immutable, hash-chained ledger. A forged "Gilligan read the policy" or "Skipper accepted this evidence" becomes permanent, auditor-facing proof that the named person never gave.
   - Fix: Add a `rejectWhenImpersonating` preHandler on routes where the act means "this specific person vouches": attest, manual-evidence create and supersede (uploader statement), link review, assertion confirm and reject, questionnaire approve, auditor-room create, trust-page publish. Return 403 `IMPERSONATION_NOT_ALLOWED`. Record `impersonator_id` on `bastion_audit_log` for every other write.

4. **[security] MAJOR - The "a human decides" boundary for fix proposals can be bypassed by agents or a forged internal event.**
   - Where: §2.4, §2.7 ("deciding the proposal" needs a human), §8.2, §7 `bastion-proposal-reconcile`, §5.1 row 90.
   - Why it matters: `proposals.routes.ts:236,275` lets any user whose role is owner or admin decide any proposal. That includes an admin-role service account using the `proposal_decide` MCP tool, so an agent can approve its own `bastion.fix.*` proposal, and Bastion then creates Bam tasks. `proposal_create` lets any agent mint a proposal with `proposed_action = 'bastion.fix.evidence_request'`. `/bastion/api/v1/internal/events` is reachable from the internet through nginx (Bursar has no deny rule, `nginx-with-site.conf:529`). It is guarded only by the `INTERNAL_SERVICE_SECRET` that about 25 services share, so a forged `proposal.decided` payload could flip drafts to approved.
   - Fix: Treat the event as a wake-up signal only. Re-read `agent_proposals` by id and act only when the id equals a `bastion_fix_drafts.proposal_id` Bastion itself wrote, `decided_by` resolves to `users.kind = 'human'`, and the decision was not made while impersonating. Add `location ~ ^/bastion/api/v1/internal/ { return 404; }` to all three nginx confs.

5. **[security] MAJOR - Attacker-controlled text reaches the LLM that drafts Bolt rules, and Bolt rules can send data out.**
   - Where: §2.4 `bolt_rule` and `policy_draft`, §2.8 (the injection pre-scan covers only questionnaires and custom framework documents).
   - Why it matters: The fix-draft prompt includes cited labels that outsiders control: GitHub PR titles from outside contributors (PR #42 in the seed), Blip tracked-app names, API key names, vendor names. Bolt actions include `send_webhook` to any public URL (`event-catalog.ts:3695`; the guard in `automation.service.ts:93-99` only blocks private addresses), `send_email_notification`, and any of about 885 MCP tools. A PR titled with instructions can produce a "turned off" rule that someone switches on, and it then ships data to an outside URL. "Created disabled" is not a security boundary.
   - Fix: Make `bolt_rule` fixes deterministic: a closed set of rule shapes in code, keyed by `(gap_kind, probe_key)`, whose actions come from a small allowlist (task create, Banter post to an internal channel). The LLM writes only the name and description. Reject any draft whose actions are outside that allowlist; never allow `send_webhook` or `send_email*`. Run `injection-prescan` over every cited label before it enters any prompt, and pass labels inside a delimited data block.

6. **[security] MAJOR - The auditor room's brute-force and scope controls don't work as written.**
   - Where: §5.2 table (lockout per IP, optional 6-digit passcode, `include_restricted`), §4.1 `bastion_auditor_rooms`.
   - Why it matters: **IP keying is broken.** bastion-api copies the Bursar skeleton, and no satellite sets `trustProxy` (only `apps/api/src/server.ts:101`). Every request therefore arrives from the nginx IP, so the "10 misses per IP" lockout shuts out every auditor for 15 minutes (a self-inflicted outage), and `ip_hash` records the proxy. With a plain `trustProxy: true`, the left-most `X-Forwarded-For` is spoofable and the lockout can be dodged. **The passcode is the guessable part, not the 256-bit token.** A per-IP counter lets a leaked link's 10^6 passcode space be worked through from many IPs. **Rooms outlive their creator's authority.** A room stays live after its creator is demoted or deleted. **Restricted scope drifts.** `include_restricted` with `control_ids` silently exposes restricted evidence uploaded after the room was created, even though the dialog listed specific items.
   - Fix: Set `trustProxy` to one hop, or the nginx address range. Add a per-room failed-passcode counter (for example 5 misses locks the room and notifies the creator). Re-check on every room request that the creator still has `auditor_room.create`; if not, return 404. Store restricted exposure as a frozen `restricted_evidence_ids uuid[]` allowlist. Filter cited refs through `can_access` with the creator as asker. Verify every `:id` in rows 86-87 belongs to the room's controls and period, not merely the same org.

7. **[security] MAJOR - Uploaded evidence files can run scripts on the app's own origin, including from the public room.**
   - Where: §5.1 rows 28, 75, 87 (`?download=1`), §3.3 (the content type comes from Bin).
   - Why it matters: Bin serves bytes `inline` with the stored content type (`apps/bin-api/src/routes/assets.routes.ts:332,346`). If Bastion copies that, an uploaded HTML or SVG file opens on the app domain (the domain that carries every session cookie) when an admin or auditor clicks it. That is stored XSS, reachable from a public link.
   - Fix: Every Bastion byte stream sends `Content-Disposition: attachment`, `Content-Security-Policy: sandbox; default-src 'none'`, and `X-Content-Type-Options: nosniff`, with a content-type allowlist (pdf, csv, png, jpeg, plain text, json); anything else is sent as `application/octet-stream`. Apply the same headers to the export zip.

8. **[security] MAJOR - The feed API makes an HR or MDM cron job hold an owner- or admin-level key.** (Same finding as design #9.)
   - Where: §3.5 ("a normal `bbam_` API key whose user holds `bastion.feed.write`"), §5.5 (`feed.write` is floored).
   - Why it matters: Only owners and admins get `feed.write`, so the HR export script must carry an owner's or admin's `bbam_` key. That key can do anything in the org on every app. A key sitting in a cron job on an HR box is the most likely credential to leak, and it can also write forged "evidence" into an immutable ledger.
   - Fix: Use Blip's ingest-key pattern (`apps/blip-api/src/db/schema/blip-ingest-keys.ts`): a per-feed bearer token, stored hashed, shown once, with rotation and a grace window. It can only push records to that one `feed_key`, and it is recorded on each `bastion_feed_records` row as `ingest_key_id`. Drop the `bbam_` path for row 37. Also bound the batch (the spec says 500) by bytes, with a per-key rate limit.

9. **[security] MAJOR - Immutable evidence holds personal data with no lawful way to remove it, and the spec's own retention job is blocked by its triggers.** (Overlaps stability #4.)
   - Where: §3.4 four-path immutability, §3.5 (`hr_roster`, `subject_user_email`, 16 KB `attributes`), §3.1 cited refs (person names), §7 `bastion-retention`, §14 ("v1 never deletes evidence").
   - Why it matters: Names, emails and HR roster attributes end up in tables that reject DELETE and UPDATE, inside objects whose hashes are chained. An erasure request, or offboarding an org, cannot be honored without disabling triggers, which is exactly the tamper the ledger is meant to expose. The retention job also deletes from `bastion_auditor_access_log`, which the spec makes reject DELETE. The first run will fail, and the obvious workaround is a trigger-bypass switch.
   - Fix: Split personal data from what the ledger proves: put labels, emails and attributes in a separate, mutable, org-scoped table keyed by id. The ledger hashes only an HMAC commitment of that data, so redacting it leaves the chain verifiable and marks the entry "redacted". Define one audited redaction route, owner-only with confirm, that writes its own ledger entry. Make the access log append-only but prunable through a `SECURITY DEFINER` purge function that the retention job alone may call.

10. **[security] MINOR - Evidence detail leaks to viewers through explanations and lists, and tamper detection is weaker than described.**
    - Where: §6.2 `explain()` ("'Coconut Radio Bridge' (210 days)"), §5.1 rows 10 and 26, §3.4 hash formula and "External witness".
    - Why it matters: `explain()` text appears on control status, which only needs `control.read` (viewer-granted, and also the `bastion_control_status` tool), so key and person names get past the `read_detail` gate. Row 26 lists restricted items' titles and owners to `evidence.read` holders. The entry hash concatenates fields with no separators and leaves out `organization_id` and `seq`, so different field values can produce the same input. The external witness is opt-in, and `ledger.sealed` lands in a Bolt table the same DBA controls, so by default a rewritten chain cannot be detected.
    - Fix: Build `explain()` from counts only, unless the viewer has `read_detail` or owns the control. Hide restricted titles in lists without `read_restricted`. Hash a canonical JSON of `{org, seq, kind, id, content_sha256, prev, recorded_at}`. Sign each sealed head with a key held outside the database (env), and print the signed head history into the export packet's `manifest.json` and the auditor room, so an auditor can check heads they have already received.

   - Why it matters: `apps/api/src/routes/upload.routes.ts:187-222` does `getFileStream(env.S3_BUCKET, key)` with only `requireAuth` plus `shadowOnly('bam.file.list')`. Shadow mode does not enforce anything, and there is no org check. Object keys are content hashes, and those hashes are exactly what Bastion shows in the ledger, `verify` and `manifest.json`. A user in another org, or anyone holding an auditor packet, can therefore download restricted HR or pen-test evidence and whole export zips through `/files/`. That skips the auditor access log and the restricted-evidence gate, and lets nginx and browsers cache the files for a day.
   - Fix: Give Bastion its own bucket: `BASTION_S3_BUCKET`, default `bigbluebam-bastion`, with an env hint, using `createBootstrapDriver` with that bucket (the S3 driver's `ensureBucket` creates it). Treat cross-bucket copy from Bin as stream-plus-hash, not `copyTo`. Separately, file an issue to deny `*/bastion/*` keys in `/files/*` and to enforce an org-prefix check there.

3. **[infrastructure] MAJOR - In the compose nginx config, `bastion-api` is a hard-coded upstream, so if it is missing or crash-looping, nginx fails to load and every app goes down. The spec handles this with a manual ordering note instead of fixing the config.**
   - Where: §9.1, §9.2 (the "Ordering is mandatory" note)
   - Why it matters: The ordering note only helps whoever is applying the change by hand. Anyone who pulls the commit, and every fresh `docker compose up`, starts nginx and bastion-api together. The spec never adds `bastion-api` to `frontend.depends_on`; Bursar has it, with `service_started`, at `docker-compose.yml:310-317`. A crash-looping container is not attached to the network, so its name fails to resolve and the whole suite returns errors.
   - Fix: Add `bastion-api: condition: service_started` to `frontend.depends_on`, with the Bursar comment. In `nginx-with-site.conf`, write `/bastion/api/` as `resolver 127.0.0.11 valid=10s; set $bastion_up bastion-api:4024; rewrite ^/bastion/api/(.*)$ /$1 break; proxy_pass http://$bastion_up;`. Railway's generated config already uses this shape. A dead bastion-api then returns a 502 on its own routes only. Keep `nginx -t` as the gate.

4. **[infrastructure] MAJOR - The spec says to hand-edit `nginx.railway.conf`, but that file is auto-generated. It also leaves `/bastion/` out of the `index.html` no-cache rule.**
   - Where: §9.2, §11.5
   - Why it matters: The header of `infra/nginx/nginx.railway.conf` says "AUTO-GENERATED by scripts/gen-railway-configs.mjs ... do not edit by hand". A hand-written `$rw_upstream_N` will be overwritten or collide with the generator's numbering. The generator only rewrites hosts that are already in `services.mjs`, so the catalog entry has to exist before you run it. Separately, `nginx-with-site.conf:896` (and `nginx.railway.conf:1040`) list the SPAs whose `index.html` gets `no-cache`. That list does not include `bastion`, and already misses basis, braid, bulwark, burn and bursar. Browsers will keep serving a stale `index.html` that points at hashed assets that no longer exist after a deploy.
   - Fix: Edit only `nginx-with-site.conf` (plus `nginx.conf`), add the `services.mjs` entry, then run `node scripts/gen-railway-configs.mjs`. That also writes `railway/bastion-api.json`; commit it. Add `bastion` to both the 896 and 907 regexes. Record the five missing siblings in the 896 regex as a separate task.
   - Orchestrator: the five missing siblings filed as issue #127.

5. **[infrastructure] MAJOR - Two CI gates in `lint.yml` would fail on the M0 commit.** (Same as best-practices #2 and #5.)
   - Where: §9.4 env hints, §9.6, §12 M0
   - Why it matters: `pnpm check:env-hints` requires a hint for every variable in a service's catalog `env`. Its allowlist is frozen ("APPEND FORBIDDEN"). The spec adds hints only for `BASTION_API_INTERNAL_URL` and `BASTION_API_URL`. It has none for `BASTION_LLM_TIMEOUT_MS`, `BASTION_ENGINE_TIMEOUT_MS`, `BASTION_PROBE_TIMEOUT_MS` or `BASTION_ROOM_IP_SALT`, so CI goes red and Railway quietly omits those variables. Second, `pnpm check:app-completeness` (`lint.yml:78`) fails any app listed in `LAUNCHPAD_CATALOG` that lacks MCP tools, `help.md`, a help index, `site/src/components/sections/<app>-section.tsx` and screenshots. M0 adds the Launchpad entry, but tools and help arrive in M8 and M9. The marketing section is not in the spec at all.
   - Fix: Add `literal` hints for the three timeouts. Give `BASTION_ROOM_IP_SALT` its own `secret` hint, generated per service, rather than deriving it from `SESSION_SECRET`. Move the `LAUNCHPAD_APP_IDS`/`LAUNCHPAD_CATALOG` change to M9; `/bastion/` still works by direct URL before then. Add `site/src/components/sections/bastion-section.tsx` and `site/public/screenshots/bastion/` to the §9.6 checklist.

6. **[infrastructure] MAJOR - The per-IP lockout on the auditor room will see the proxy's IP, not the client's. Ten bad tokens from anyone would lock out every auditor at once.** (Same as security #6.)
   - Where: §5.2 (Redis per-IP failed-token counter, 120 req/min per IP)
   - Why it matters: The Bursar skeleton has no `trustProxy`; only `apps/api/src/server.ts:101` sets it. nginx has no `real_ip` setup. So `request.ip` is the nginx container on compose, and the ingress on Railway, where an edge proxy sits in front of nginx. If you set `trustProxy: true` naively, Fastify takes the left-most `X-Forwarded-For` value, which the client controls, so the lockout can be bypassed.
   - Fix: Add `TRUST_PROXY_HOPS` (compose 1, Railway 2; give it an env hint) and pass `trustProxy: <hops>` to Fastify. Add an integration test where two different forwarded clients see independent lockout counters.

7. **[infrastructure] MAJOR - Evidence would not survive a platform backup and restore. Backups cover Postgres only, and the spec says nothing about objects or about rewinding the ledger.**
   - Where: §3.4, §2.2, §15 (no DR section)
   - Why it matters: `apps/worker/src/jobs/backup-database.job.ts` runs `pg_dump` and nothing else. If MinIO is lost, every `verify` and `bastion-ledger-verify` reports `evidence.integrity_failed`. If the database is restored to an earlier point, the ledger head falls behind the `ledger.sealed` hashes already sent to webhooks and Banter. Both cases produce a flood of false tamper alarms, which is the one signal a compliance product cannot get wrong. There is also an irony here: Bastion's own `ops.backup_fresh` probe would certify backups that do not include its evidence.
   - Fix: Add a §9.7 on backup and DR. Back up the Bastion bucket alongside `pg_dump`, for example by extending the backup job to mirror `bastion/` objects. Make the verifier record "object missing" separately from "hash mismatch". After a restore, append a `restore` entry to the ledger that cites the prior sealed head, so a rewind is explained rather than flagged as tampering.

8. **[infrastructure] MAJOR - The nightly evaluator, LLM work and export packets have no capacity plan. They share a global LLM cap, the primary database, and the memory of a single process.**
   - Where: §7 (evaluate-tick, autofill, export-packet), §7.2, §4.1 settings (`max_llm_calls_per_questionnaire` 1200), §9.1
   - Why it matters: The internal LLM cap is per calling service, not per org: 4 concurrent calls and 120 per minute by default (`apps/api/src/env.ts:115-116`). One org's 1,200-call questionnaire therefore holds every other org's compile and autofill for about an hour. Probes are raw SQL against the primary database (scans of `v_activity_unified`, `login_history` and `bolt_executions`), and every org that keeps the default `evaluation_hour_local` lands in the same 15-minute tick. jszip builds the whole archive in memory, including restricted PDFs. The spec puts engine logic in bastion-api, which has no memory limit.
   - Fix: Add per-org fairness in front of the proxy, for example a Redis per-org slot or BullMQ grouping, and state the expected throughput in the spec. Run probes on `DATABASE_READ_URL` when it is set, with `SET LOCAL statement_timeout = BASTION_PROBE_TIMEOUT_MS`, and spread the default evaluation minute by a hash of the org id. Stream the zip with `generateNodeStream({streamFiles:true})` straight into `driver.put`. minio does a multipart upload when the size is unknown. Cap packet bytes and say which container builds the packet.

9. **[infrastructure] MINOR - Two build and pipeline details would break M3.**
   - Where: §12 M0 ("copy of bursar-api skeleton"), §3.3, §7 `bastion-evidence-ingest`
   - Why it matters: `apps/bursar-api/Dockerfile` does not copy or build `packages/storage`; `apps/bin-api/Dockerfile:16,31,41,58` does. A Bursar copy therefore will not compile `@bigbluebam/storage`. Railway's `watchPatterns` also ignore `packages/storage` and `packages/permissions`, so changes there will not redeploy bastion-api. The worker's default AV mode can be set to `off`, which marks assets `skipped`. The four-check copied from Bursar accepts only `clean`, so with AV off every upload stays `pending_scan` and gets retried every 10 minutes forever.
   - Fix: Add the four `packages/storage` lines from bin-api to the Dockerfile, and add `extra_watch_patterns: ['packages/storage/**','packages/permissions/**']` to the catalog entry. Define what happens for `skipped` and `error`: either accept `skipped` with a "not virus-scanned" label on the evidence, or show a plain-language blocked state. Cap ingest retries and record each failure through `recordWorkerError`.

Confirmed sound by the infrastructure reviewer: ports 4024 and 3024 are not used anywhere in apps, packages, scripts or infra. The `/health` healthcheck, the `curl` dependency it needs, and the readiness scope copied from Bursar are correct.
