# Bastion spec review - round 2

Spec under review: `docs/brainstorming/2026_11_25_20_03_APP_DESIGN_bastion.md` after the round-1 fold-in (09bb0791). The same five reviewers each verified their own round-1 findings against the text, then looked for new problems. Findings are verbatim.

## Design

**Round-1 verification:** all nine design findings are fixed in the text itself, not only in the changelog. Three of the fixes left a hole (findings 1, 4, 6 below). design-7 was checked against `beacon_visibility` (has `Public` and `Organization`, default `Project`).

1. **[design] MAJOR - An accepted exception turns a control into "Proven by evidence you provided". That blends accepted risk into proof and can lead the questionnaire to draft a confident "Yes".**
   - Where: §2.6 ("status becomes `pass` ... counts under 'Proven by evidence you provided'"), §2.3 four-number table, §2.7 step 6, §11.4 story 6 ("counts as provided")
   - Why it matters: An exception is management's statement that the control is *not* operating for that item. Counting it as proof contradicts §1.3 ("the coverage graph never blends sources"), and it makes the home numbers rosier than what the auditor will record ("exception noted"). Because the effective status is `pass`, §2.7 banding allows a `high` "Yes" for a control with an accepted exception, which breaks "never a confident Yes it cannot prove". It is also unbounded. An exception can cover "the whole failing assertion" for up to 365 days, and nothing says it is limited to the failures that existed at approval. A year-long assertion-wide exception therefore hides every new failure, which amounts to the threshold-loosening §2.6 says it prevents.
   - Fix: Keep the effective status `fail`, shown as "Not met, risk accepted". Either count it under Not met with an "N accepted" sub-count, or add a fifth number. Accepted exceptions do not create a `failing` gap, but they stay visible. Questionnaire: any cited control with an active exception is capped at `medium`, and the draft names the exception. Freeze the cited set at approval: an assertion-wide exception covers only the refs failing at approval, recorded on the row. Cap assertion-wide exceptions at 90 days and keep 365 days for single-entity ones. Update §2.3, §2.7, §10.3 expectations and story 6.

2. **[design] MAJOR - Controls with no confirmed assertion drop out of the four numbers and the gap list, so the home screen can show 100% proven while half the framework has never been assessed.**
   - Where: §2.3 ("Controls with no confirmed assertion are excluded from all four numbers and from the gap list"), §6.1 Readiness, §5.4 `bastion_coverage_summary`, §8.1 `readiness.weekly`, §5.2 auditor room
   - Why it matters: Round 1 asked for setup work to stop flooding the gap list. The fix went further and made unassessed controls disappear. An org that confirms the easy checks and rejects or ignores the hard ones (encryption, MFA, vendor review) sees only green numbers. A control whose assertions were all rejected never shows up again, except as a gap in a progress bar people learn to ignore. Agents reading the summary tool and the weekly Banter digest get the flattering ratio with no denominator.
   - Fix: Treat "Not set up yet" as a visible state with its own count, shown next to the four numbers ("41 of 64 controls checked; 23 not set up") everywhere those numbers appear: Readiness, MCP summary, `readiness.weekly`, the packet, and the auditor room as "Not assessed". After a setup grace period (e.g. 14 days after the framework is adopted), add a `not_assessed` gap kind with low severity (0.30) and fix template `process_change`/confirm, so unassessed high-risk controls rank without drowning the list on day one. A control whose assertions were all rejected goes straight to `not_assessed` with no grace.

3. **[design] MAJOR - The `stale` gap maps to `process_change`, whose approval turns the control into a manual assertion. One stuck worker can therefore produce dozens of proposals that rewrite controls.**
   - Where: §2.3 mapping row `evaluation_stale -> stale -> process_change`, §2.4 (`process_change` approval "Becomes a manual assertion")
   - Why it matters: Staleness hits every control at once when the evaluator stops. Each one gets a cost-5 LLM-drafted procedure, and approving any of them converts a native control into manual. That is the wrong fix for an infrastructure fault, and it is inconsistent with `check_broken`, which correctly has no template.
   - Fix: Map `stale` to template `none` (operator issue), like `check_broken`. Collapse it into one org-level Readiness banner (already in §6.1) and one `evaluation.missed` worker error, not one gap per control. Optionally keep a single org-level gap row.

4. **[design] MAJOR - The fix for detecting review subscriptions still fails for every existing GitHub integration, so pre-existing installs keep the original "team never reviews means not connected" bug.**
   - Where: §3.1 `change.merge_reviewed` precondition ("from the stored `ping` `hook.events`, or any review delivery ever received"), §8.4 / migration 0261
   - Why it matters: GitHub sends `ping` only when the webhook is created. Webhooks created before migration 0261 never send it again, so `subscribed_events` stays NULL. On those installs, a team that is subscribed to reviews but has never approved a PR again gets `unprovable/not_connected`, and the drafted fix ("tick Pull request reviews") is one they already did. Those installs are exactly the population the §10.2 seed and existing customers represent.
   - Fix: Treat a NULL `subscribed_events` as its own state, "unknown", never as "not subscribed". The `connect_source` text for "unknown" says: "In GitHub, open the webhook's Recent Deliveries and click Redeliver on the ping". A redelivered ping carries `hook.events`. Until a ping is seen, run the predicate anyway. Merges with zero approvals yield `fail`, with `explain()` noting "we could not confirm GitHub sends review events". The precondition rule holds because the absence of reviews is not what decides "not connected". Add the NULL case to the §11.2 goldens.

5. **[design] MAJOR - Redacting personal data deletes the bytes of a manual evidence item, but the item stays `active` and keeps proving the control.**
   - Where: §3.4 personal data ("blanks the data, deletes any manual-evidence bytes"), §3.3 manual assertion evaluation (requires an `active`, accepted item), §4.1 `bastion_manual_evidence.status`
   - Why it matters: After redaction, the control still shows "Proven by evidence you provided" from a file that no longer exists. The auditor room and packet then offer a "redacted" object as the proof, which an auditor will reject. Redaction also becomes a quiet way for an owner to destroy evidence without the control status reacting. It is ledgered, but the home numbers do not move.
   - Fix: Redacting a `manual_evidence` holder sets its status to `withdrawn` (reason `redacted`) in the same transaction and enqueues control-scope runs for every linked assertion. A new evaluation then gives `manual_evidence_missing` unless another item covers it. Redacting snapshot or attestation labels does not change outcomes (the commitment remains); state that explicitly. Add the case "redact the only accepted file: the control drops to Can't prove yet" to §11.1.

6. **[design] MAJOR - Population is confirmed once and never revisited, so a repo or tracked app connected later is silently left unchecked.**
   - Where: §3.1 population rule, §2.1 step 5 (the fallback proposes the population "from what the compiler finds connected"), §2.1 (confirmed assertions are content-immutable)
   - Why it matters: `expected_population` lives inside immutable assertion params. When a team integrates a new repo next quarter, its merges are never evaluated, and the control keeps saying "2 repositories checked" while a third ships unreviewed code. This is the same undercount as round 1, only delayed. The deterministic fallback also seeds the population from exactly the connected set, so without the LLM the only safeguard is the wizard's free-text "add any we missed".
   - Fix: Each population probe also returns the connected-but-not-expected members (`population_unlisted`). Any unlisted member yields a new `population_drift` gap (severity about 0.70, template `config_change`: "Add 'Coral Reef Booking' to the repositories Bastion checks"). Approving it files a superseding assertion with the new population for one-click confirmation. Add a required "This is the complete list" confirmation, stored as `population_confirmed_at`/`_by` in the params. A `population_review` gap opens after 180 days so the list gets re-confirmed.

7. **[design] MAJOR - Applicability is per control, but ISO 27001 needs per-requirement applicability (the Statement of Applicability), which the shared-control model cannot express. No SoA is produced.**
   - Where: §2.1 option (b), §4.1 (`bastion_controls.applicability` / `not_applicable_reason`; `bastion_control_requirements` has no applicability), §7.2 packet
   - Why it matters: Under ISO 27001 every Annex A control must be marked applicable or excluded, with a justification, in a Statement of Applicability. That is the first artifact an ISO auditor asks for. With applicability on the shared control, an org cannot exclude A.7.x (physical) while keeping the same internal control applicable for a SOC 2 criterion, or the reverse. And because the packet has no SoA, the ISO half of the "second framework" journey (§1.2) dead-ends at the auditor.
   - Fix: Add `applicability` and `not_applicable_reason` to `bastion_control_requirements`. A control counts in a framework's view only through its applicable requirement links. Its org-level applicability becomes derived: N/A only when every link is N/A. Generate `statement_of_applicability.csv` (ref_code, title, applicable, justification, implementing control, current status) in the ISO packet and the auditor room. Add a unit test that every Annex A requirement has an applicability decision before an ISO packet can be built.

**Minor (design):**
- Archiving a framework (§2.1, row 6) leaves controls whose only links are to that framework; say they become "Retired" and drop out of all numbers, gaps, and evaluation.
- §2.7 step 8 marks answer-library entries stale "when any cited control changes status". Since staleness is computed when status is read, one missed night could mark the whole library stale. Restrict this to stored-status changes and exclude `evaluation_stale`.
- The `stale` gap is computed by `bastion-gap-rank`, which may be the job that stopped. Derive stale gaps at read time from `effectiveStatus`, not from the ranked table.
- §2.4 says fix approval needs "the control owner or `control.write`", but §2.6 never names the approver (`approver_id`) for an exception proposal. State it: the control owner proposes or is notified, and a floored `exception.approve` holder decides.

## Security

**Round-1 verification:** nine of ten resolved in the text. **security-4 is not resolved**: the fix as written cannot be built (finding 1 below). Detail: security-1 resolved (§8.4 #123, §3.3 random `objects/<uuid>` key, §9.1 own bucket, §11.2 negative test); security-2 resolved (SECURITY DEFINER functions in 0267, goldens run twice; leftovers in minors); security-3 resolved for bastion-api's own routes (the exception-approval reconcile is a background job that depends on security-4); security-5, 6, 7, 8 resolved; security-9 resolved as adapted (leftovers in minors); security-10 resolved, but the new restore path creates finding 2.

1. **[security] BLOCKER - The re-check of proposal decisions reads data that does not exist, so agents can still approve exceptions and fixes.**
   - Where: §2.8 "Proposal decisions are re-verified" (conditions 2-4); §2.6 exceptions; §11.1 "proposal re-verification (agent decider, impersonated decider ... rejected)".
   - Why it matters: Condition (2) checks `approver_id`. That is the *designated* approver, not whoever decided. `agent_proposals` has no `decided_by` column at all (`apps/api/src/db/schema/agent-proposals.ts:27-48`). `proposals.routes.ts:275` lets any owner, admin or SuperUser decide a proposal regardless of `approver_id`. That includes an admin-role service account using `proposal_decide`. The update at `:317-326` stores only status, `decided_at` and reason. Nothing is written about impersonation. The decider appears only as the actor on the `proposal.decided` Bolt event (`:343-345`). That event arrives through `/internal/events`, which is transport, not a record. Under impersonation the actor is the impersonated human, recorded as a `'user'`. So conditions (2)-(4) always pass for a human approver. Exceptions are the damaging case: an approved exception turns a `fail` into `pass` and counts as "Proven by evidence you provided". An agent with an admin-role key can therefore turn controls green. The §11.1 unit test can only pass against a mock.
   - Fix (pick one; the first is cleaner): (1) Bastion owns the decision. Add `POST /fix-drafts/:id/decide` and `POST /exceptions/:id/decide` to bastion-api, each with `requireCan` on the matching permission, `rejectWhenImpersonating`, and a `users.kind = 'human'` check on `request.user`. Bastion then closes the mirrored `agent_proposals` row itself, and ignores any `proposal.decided` for a `bastion.*` action that it did not make. In the surface map, mark Bastion proposals as "decide in Bastion". (2) Platform change in M0, filed as an issue. Add `decided_by`, `decided_by_kind` and `decided_impersonator_id` to `agent_proposals` through a new migration, set them in the decide route, and have Bastion read those columns. This also benefits every other consumer of proposals.
   - Orchestrator: confirmed and filed as issue #128. Direction for the fold-in: do both. The platform columns (option 2) land in M0 as the fix to the fact, and Bastion's high-stakes decisions (exceptions, and any fix that changes control status) are decided in Bastion (option 1) so the human-only rule is enforced at the point of decision, with the mirrored proposal closed by Bastion.

2. **[security] MAJOR - The automatic `restore` ledger entry can disguise tampering as a routine restore, and the restore check compares the database against itself.**
   - Where: §3.4 "Restores", §9.7 bullet 3, §4.1 `bastion_ledger_seals`.
   - Why it matters: The check compares the ledger head with the latest seal row. Both live in Postgres, so a real restore rolls them back together and nothing is detected. Later appends then reuse `seq` values already covered by seals that were published and signed. Auditors who hold an earlier packet see two different signed chains, which looks like tampering when it is a restore. In the other direction, someone with DBA access can delete trailing ledger rows (triggers disabled). The service then appends a `restore` entry and publishes `ledger.restored` on its own, so the rewrite is labelled a benign restore. That is the exact attack the seals exist to expose.
   - Fix: Write each signed seal as an object outside the database as well (`seals/<org>/<date>.json` in the Bastion bucket, which is mirrored separately per §9.7). Compare the database head against that copy. Add an `epoch` field to the canonical form, so entries after a restore never reuse a sealed `seq`. Allow a `restore` entry only when a completed `platform_restores` row lines up with the gap, and only after an owner who is not impersonating acknowledges it. Show the lost `seq` range in the auditor room and the packet as "History lost by restore, seq X-Y". Never mark it benign automatically. Without a matching restore record, raise `evidence.integrity_failed`.

3. **[security] MAJOR - Exceptions let one person turn a failing control into a confident "Yes" that goes outside the company.** (Overlaps design-1 in this round.)
   - Where: §2.6 (an exception yields `pass`), §2.7 step 6 (banding uses effective status), §5.5 `exception.propose` (member) and `exception.approve` (owner/admin).
   - Why it matters: Once an exception is active, `effectiveStatus` returns `pass`. Questionnaire autofill then bands answers citing that control as `high`, and a customer receives "Yes, laptops are encrypted" because someone accepted the risk. That breaks the spec's own promise that Bastion never drafts a confident "Yes" it cannot prove. Nothing stops the same admin from filing and approving an exception. A one-line reason can cover a whole assertion for up to 365 days.
   - Fix: Make "passing only because of an exception" its own effective state (`pass_with_exception`). Questionnaire banding forces it to `medium` at most, and the draft must say "accepted exception: {reason}". Require the approver to be different from the proposer, with the same under-three-humans exception and the same "small team" label as manual evidence. Show the exception owner and expiry on every surface that shows the control as passing.

**Minor (security):**
- Definer probe functions: add `REVOKE EXECUTE ... FROM PUBLIC` and grant only to the app role; use `SET search_path = pg_catalog, public, pg_temp` with `pg_temp` last; the "visibility floor" compares the definer path against itself so it can never fail: compare against the active-member count on the people page, or drop it.
- The access-log purge guard is a custom setting anyone can set (`SET LOCAL bastion.purge_access_log='on'`). The two-year age condition limits the damage; better, have the trigger check the caller is the purge function's owner role.
- The room-token and feed-key lookups run before the org is known. Under `BBB_RLS_ENFORCE=1` they return zero rows (room 404, feed 401): the #105 problem again, fail-closed but inviting a bypass. Specify `SECURITY DEFINER` resolver functions returning only `(id, org_id)` (`bastion_resolve_room(token_sha256)`, `bastion_resolve_feed_key(key_id)`).
- `object_missing` is treated as an infrastructure event, so deleting an evidence object (all services share the S3 credentials) never shows as tampering. Show it to the auditor as "evidence file missing".
- Personal-data commitments are not checked on read. Add a `pd_mismatch` result to verify and to rendering.
- Redacted evidence whose bytes were deleted should stop counting toward `pass` (same as design-5 this round).
- Seal key rotation: `GET /ledger/seals` serves a single public key. Publish every `signing_key_id` with its public key in the packet, so old seals stay verifiable after a key change.
- Feed-key pepper: the `secret_hmac` "server pepper" has no env var or `secret` hint in §9.4.
- Passcode lockout: "5 misses lock the room" lets anyone holding the link lock out the real auditor. Add a creator-side **Unlock** in the access-log view.
- `GET /policies/:id/body` keeps serving an article whose Beacon visibility was narrowed until the next night's run. Re-check visibility on each request.

## Stability

**Round-1 verification:** all nine are addressed in the body. Five fixes have a hole, covered below: stability-1 (slice budgets: fixed in §7.3, but "whole controls per slice" breaks the budget again, finding A); stability-2 fixed; stability-3 fixed (the nightly unique index blocks retrying a failed night, finding B); stability-4 fixed (sweep unbounded with a restore hazard, finding D; quota counter never resets, minor); stability-5 fixed; stability-6 fixed (no ordering between outbox rows, finding E); stability-7 fixed (the restore detection added alongside cannot work, finding C); stability-8 fixed (worker lacks the env it needs, finding G); stability-9 fixed.

A. **[stability] MAJOR - Keeping a control's assertions in one slice breaks the probe time budget, and the write phase after each probe has no budget at all.**
   - Where: §7.3 ("a slice takes whole controls ... never split across slices"; "worst case 15 + 8 = 23 s"), §3.4 (writes to the bucket happen before the ledger transaction; the per-org advisory lock), §3.5 (feed batches of 500).
   - Why it matters: "Stop starting probes at 15 s" cannot hold if a control must finish inside one slice. A control with 4 probe assertions started at 14 s ends at 14 + 4 x 8 = 46 s. That is past `BASTION_ENGINE_TIMEOUT_MS` (30 s), which brings back exactly the abort, 409 and reaper loop that round 1 fixed. The budget also leaves out the work after each probe: the object `put`, which has no timeout and can hang on a slow MinIO; waiting for `pg_advisory_xact_lock`, which a 500-record feed batch can hold; the conditional status update. `SET LOCAL statement_timeout` applies only to the read-only probe transaction, not to that waiting. This splitting rule is unnecessary anyway: §2.2 already says status is aggregated only after every assertion of the control has a snapshot in the run, so assertions can be split across slices safely.
   - Fix: Allow a control's assertions to span slices. A slice takes assertions in control order and stops starting probes at 15 s. A control is aggregated in whichever slice writes its last missing snapshot (count the run's snapshots against the control's confirmed assertions inside the conditional update). Add `SET LOCAL lock_timeout = '3s'` on the ledger append transaction; on timeout end the slice cleanly (not a probe error). Wrap every `put` in a timeout (for example 5 s). Restate the invariant as `15 + probe timeout + per-assertion write budget < engine timeout`, and extend `test/time-budgets.test.ts` to cover it.

B. **[stability] MAJOR - A nightly run that ends `partial` or `failed` cannot be retried the same day. One blip at 03:00 therefore turns every control stale before the next run.**
   - Where: §4.1 partial unique index `(organization_id, nightly_for_date) WHERE trigger = 'nightly'` (it applies to every status), §3.2 (`storage_unavailable` makes the run `partial`), §7 `bastion-run-reaper` (moves runs to `partial`), `stale_after_hours = 36`.
   - Why it matters: the last good run is day 1 at 03:00. On day 2 at 03:00, MinIO, a deploy or the reaper leaves the run `partial`. The index then forbids another nightly row for that date, and the tick only claims dates that have no row. The next run is day 3 at 03:00, 48 h after the last good one, which is past 36 h. From about 15:00 on day 2, every control shows "Can't prove yet / evaluation_stale": the four home numbers collapse; questionnaire banding forces every answer to `low`; the auditor room shows everything unprovable; `evaluation.missed` fires. All of that comes from a 2-minute storage outage.
   - Fix: make a `partial` nightly run resumable. When the tick finds the day's nightly row in `partial`, with `nightly_for_date` still today in the org's timezone and `resume_count` under 3, it sets the row back to `queued`, keeps its `as_of`, and re-enqueues it with `jobId = run.id + ':' + resume_count`. Slices skip assertions that already have a snapshot in this run, which makes the resume idempotent. The reaper sets `partial` only when the attempt is truly abandoned; otherwise it releases the claim (`claimed_by = NULL`, status `queued`).

C. **[stability] MAJOR - The database-restore detection compares the ledger with seals stored in the same database, so it can never fire. After a restore, previously published seals look like tampering.** (Same root cause as security-2 this round.)
   - Where: §3.4 Restores ("compares the ledger head with the latest seal"), §9.7, `bastion_ledger_seals` (a Postgres table).
   - Why it matters: a platform restore rolls back `bastion_ledger_seals` together with `bastion_ledger_entries`, so in the database the head is never behind the latest seal. The Bolt copy of `ledger.sealed` lives in bolt-api's tables in the same Postgres and rolls back too. New entries then reuse sequence numbers that were already sealed and published with different hashes. An auditor holding an old signed seal or packet sees sequence N with a different hash, and no `restore` entry explains it. That is the exact false-tamper outcome §3.4 is meant to prevent.
   - Fix: Also write each signed seal to the Bastion bucket at `seals/<org>/<seal_date>.json`. The bucket is not rolled back by a database restore, and the write can go through the same outbox. On boot and in each seal run, compare the database head with the newest seal in the bucket. If the database is behind, append the `restore` entry citing the bucket seal. Add an integration test: seal, take a `pg_dump`, append, seal, restore the dump, boot, and check that a `restore` entry exists.

D. **[stability] MAJOR - The object sweep deletes evidence after a restore, gets slower every day, and redacting one item can destroy another item's file.**
   - Where: §7 `bastion-object-sweep` ("deletes only objects older than 24 h with no DB row"), §4.1 `bastion_evidence_objects` (primary key `(organization_id, content_sha256)`, which makes identical files share one object), §3.4 redaction ("deletes any manual-evidence bytes it belongs to").
   - Why it matters: **Restore hazard.** After a database restore, every object written after the backup point has no database row. The sweep deletes those objects 24 h later, destroying the only bytes of the lost period before anyone can reconcile. **Unbounded cost.** The only way to find orphans is to list every object under every org and run a database check per object (about 55k new objects per org per year), and the work grows every day with no limit. **Shared objects.** Identical bytes are stored once (for example the same CSV attached twice, or superseded by an identical file). Redacting one holder deletes the shared object, and the other, unredacted item then verifies as `object_missing` or `redacted`.
   - Fix: Track writes with an intent table. Insert `bastion_object_intents (org, object_key, created_at)` before each `put` and delete the intent row in the same transaction that inserts the object row. The sweep scans only intents older than 24 h, so its cost depends on failed writes, not on all objects. Pause the sweep while a `restore` entry for the org is unreconciled. Count references to each object (or check for other holders) before redaction deletes bytes; a shared object is deleted only when its last holder is redacted.

E. **[stability] MAJOR - The outbox has no ordering between dependent rows, and dead rows cannot be retried.**
   - Where: §4.1 `bastion_outbox` (independent rows, each with its own backoff of 30 s to 6 h), §2.5 (task upsert, then the "Drifted again" or recovery comment), §8.4 `POST /internal/bastion/tasks/:id/comment` (addressed by task id).
   - Why it matters: The recovery comment needs the Bam task id, which exists only after the upsert row is delivered. If the upsert is backing off or dead, the comment row fails, burns its retries and goes `dead`. Events are not ordered either. A `control.drifted` at backoff step 4 can reach Bolt after the later `control.recovered`, so Bolt rules (and the Banter routing promised in §1.5) see a recovered control as drifted. Once a row is `dead` (for example a Bam task upsert after an outage of more than 6 h), nothing ever creates the task. There is no re-drive.
   - Fix: Add an `ordering_key` column (`control:<id>` for task and drift rows, `seal:<org>` for seals). The drainer delivers only the oldest pending row for each ordering key, so a backing-off row blocks the rows behind it. Address comments by `external_id` (`bastion:control:<id>`), not by task id, so a comment does not depend on the upsert's result. Add a floored admin re-drive for `dead` rows (Settings, then Delivery problems) and record the count in `/metrics`.

F. **[stability] MAJOR - Async-start LLM slices lose work on every deploy, and the Redis semaphores can leak slots or let the run lease expire.**
   - Where: §7.3 ("the engine call returns 202 at once; the slice runs in bastion-api ... heartbeats after every call"; a Redis semaphore of 1 per org and 3 service-wide), §7 `bastion-run-reaper` (moves the run to `partial` and resets the questionnaire from `answering` to `mapping`).
   - Why it matters: **Deploys.** The slice lives only in the memory of the bastion-api process. A rolling deploy or crash drops it silently. After 5 minutes the reaper sets the run to `partial` and sends the questionnaire back to `mapping`, so a person has to notice and press autofill again. **Leaked slots.** If a pod dies while holding a semaphore slot and the slot has no expiry, it is never returned. Because the per-org limit is 1, that org can never make another LLM call. **Lease expiry while waiting.** Heartbeats happen "after every call", not while waiting for a slot. With 3 service-wide slots, a busy period of more than 5 minutes means the lease expires while the slice is still waiting, and the reaper takes the run while the slice is still alive.
   - Fix: Implement the semaphores as leases that expire: a Redis sorted set scored by expiry, each lease valid for `BASTION_LLM_TIMEOUT_MS + 10 s`, expired entries removed on every acquire, the slot released in a `finally` block. Heartbeat while waiting for a slot, and count the wait against the 150 s slice budget. On SIGTERM, stop starting LLM calls, let the current call finish, and release the claim (`claimed_by = NULL`, status `queued`). Have the reaper re-queue resumable compile and autofill runs (with a resume counter capped at 3) instead of moving them to terminal `partial`. Items already completed are kept and skipped.

G. **[stability] MAJOR - The mirror's "current" check races the backup schedule, and the worker lacks the bucket settings the packet and mirror need.**
   - Where: §9.7 (`ops.backup_fresh` passes only if the backup record shows the Bastion mirror current), §7 (`bastion-object-backup` runs at a fixed `30 2 * * *`), the backup job scheduled by `env.BACKUP_SCHEDULE_CRON` (`apps/worker/src/worker.ts:2679-2685`, configurable), §9.1 and §9.4 (the worker only gets `BASTION_API_INTERNAL_URL`), §7.2 (the packet is built in the worker).
   - Why it matters: "Current" is not defined, and the two schedules are independent. Each night's evaluation at 03:00 plus the org offset writes objects after the 02:30 mirror run. A backup that runs at any later time therefore sees the mirror as behind, so `ops.backup_fresh` fails every night and reports a real compliance failure that is only a scheduling artifact. The mirror cursor cannot come from listing the bucket, because object keys are random UUIDs and their order does not track time. Without `BASTION_S3_BUCKET` and the S3 settings for Bastion's own bucket, `createBootstrapDriver` in the worker falls back to `S3_BUCKET`. The packet job and the mirror then read and write the wrong bucket, so every packet fails with `object_missing`.
   - Fix: Define "current" as: the mirror cursor (the `created_at` of the last mirrored object, read from `bastion_evidence_objects`) is at or after the newest object created before the backup's `started_at`, minus 1 h. Have the backup job itself run a mirror pass before it records status, instead of relying on a separately timed cron. Add `BASTION_S3_BUCKET` and the S3 variables to the worker's compose service, its `services.mjs` entry and its env hints. Add an M8 smoke test: build a packet on a stack where the worker's `S3_BUCKET` differs from Bastion's bucket.

**Minor (stability):**
- `consecutive_error_nights` goes up once per run, so a manual **Check now** plus the nightly run on the same day counts as "two nights" and triggers drift. Count distinct `nightly_for_date` values, and reset the counter on success.
- `bastion-evaluation-missed` runs hourly with no deduplication, so a broken org gets 24 `evaluation.missed` events and worker errors a day. Give the outbox row an idempotency key built from the org and `last_completed_at`.

1. **[best-practices] BLOCKER - Publishing only through the outbox makes every Bastion event invisible to the catalog check, and the events aren't registered until six milestones after they start firing.**

Separately, the outbox starts publishing at M4 (seals, drift), but `bastionEvents` lands at M10. For M4-M9, bolt-api's not-in-static-catalog path (`event-ingestion.routes.ts:145`) fires on every event.

Move the `bastionEvents` registration to M4, in the same change as the outbox.

2. **[best-practices] MAJOR - The enum list still lives in two places: `BOLT_SOURCES` in TypeScript and the enum values in the migrations.**

That is the same silent-loss failure #124 is fixing.

3. **[best-practices] MAJOR - The secret hints don't match what auto-deploy generates, and two of the keys must never be regenerated.**
   - Where: §9.4 (`BASTION_SEAL_SIGNING_KEY`, `BASTION_PD_HMAC_KEY`, `BASTION_ROOM_IP_SALT` as bare `{ kind: 'secret' }`), §9.1, §9.6 `.env.example`.

The three new ones have neither. `railway-auto-deploy.mjs:145-157` fills a missing secret with `randomBytes(32).toString('hex')`. If bastion-api expects a PEM or PKCS8 Ed25519 key, the first automated deploy crash-loops. Regenerating the signing key or the HMAC key breaks verification of every published seal and every personal-data commitment. `BLIP_INGEST_PEPPER` has a "must stay STABLE" note for the same reason. An existing developer `.env` has none of these, so bastion-api fails its env check on the next `up`.
   - Fix: Define the format: a 64-hex 32-byte Ed25519 seed, which bastion-api wraps into a key object at boot. Give each hint `value: '<generate>'` and a note that says what the value is, that it must stay stable, and what breaks if it changes. Record `signing_key_id` rotation as the only supported way to change the signing key. In compose, use `${BASTION_SEAL_SIGNING_KEY:?...}`-style messages, or a documented dev default, so the failure says what to do. (Infrastructure N2 this round disagrees on `:?`; see there.)

4. **[best-practices] MAJOR - At M10 the 24 tools vanish from the generated docs catalog while the published count says 909.**

No check catches it.

5. **[best-practices] MAJOR - These are the first `SECURITY DEFINER` functions in the repo, and the spec doesn't set the safe pattern.** (Overlaps a security minor this round.)
   - Where: §3.1, §4.1 (`bastion_purge_access_log`), §4.4 `0266` and `0267`.

## Infrastructure

**Round-1 verification:** infra-1 yes (the #126 design itself has a new problem, N6); infra-2 partly (own bucket and random keys added, M0 fixes #123, but the worker never gets bucket access and the backup mirror puts evidence back into the shared bucket, N4, N5); infra-3 yes for compose, but the fix breaks Railway (N1); infra-4 yes in the text, but in practice the generator cannot handle the new block (N1); infra-5 yes; infra-6 yes; **infra-7 no**: §9.7 is in the text but two of its parts do not work (N3, N4) and the keys are not backed up (N2); infra-8 partly (semaphores have no lease and the throughput figures are wrong, N7); infra-9 yes.

N1. **[infrastructure] BLOCKER - The runtime-resolved `/bastion/api/` block passes through `gen-railway-configs.mjs` unchanged, so on Railway every Bastion API call returns 502.**
   - Where: §9.2, §12 M1
   - Why it matters: The generator only rewrites the literal form `proxy_pass http://host:port` (`scripts/gen-railway-configs.mjs`, regex `/proxy_pass(\s+)http:\/\/([a-z][a-z0-9-]*):(\d+)/`). It never touches `set $bastion_up bastion-api:4024;` or `proxy_pass http://$bastion_up;`. So the generated `nginx.railway.conf` keeps `bastion-api:4024`; on Railway the correct address is `bastion-api.railway.internal:8080`. It also keeps the location-level `resolver 127.0.0.11`, which is Docker's DNS, does not exist on Railway, and overrides the server-level `__RESOLVER__`. Every M1 gate passes anyway, because `nginx -t`, compose and "stopping bastion-api leaves every other app up" all run locally.
   - Fix: Extend the generator to rewrite `set $<var> <host>:<port>;` when `<host>` is a known service (same `.railway.internal` and 8080 mapping). Have it drop or replace any `resolver 127.0.0.11` line with `__RESOLVER__`. Add a generator unit test. Add M1 gates: `grep -c 'bastion-api.railway.internal:8080' infra/nginx/nginx.railway.conf` must be at least 1, and `grep -c 127.0.0.11 infra/nginx/nginx.railway.conf` must be 0. Do the generator change in M0 next to #127. The compose-side runtime resolver pattern is worth keeping for the other apps later.

N2. **[infrastructure] MAJOR - The three new required secrets are not produced by `deploy.sh`, and nothing keeps them stable. Losing or rotating `BASTION_PD_HMAC_KEY` permanently breaks verification.** (Overlaps best-practices 3.)
   - Where: §9.1, §9.4, §3.4, §9.7, §15.14
   - Why it matters: `generateSecrets()` in `scripts/deploy/shared/secrets.mjs` returns a fixed list without the Bastion keys. The compose adapter (`writeEnvFile`) therefore writes a `.env` without them, compose passes empty strings, and bastion-api crash-loops on fresh installs and on existing stacks after `git pull`. The interactive Railway path passes `extractSecretsFromEnvConfig(envConfig)`. A required `secret` var that is missing makes `buildServiceVariables` throw "Cannot resolve required variable", which aborts bastion-api provisioning. Only the CI `fillMissingSecrets` path works. If they are simply added to `generateSecrets()`, the rehydrate branch at `scripts/deploy/main.mjs:151-165` regenerates them on every re-run, because saved state stores them as `[REDACTED]`. A new `BASTION_PD_HMAC_KEY` makes every existing `personal_data_hmac` commitment unverifiable. §9.7 backs up the database and objects but not the keys, so a rebuilt host cannot verify its own ledger.
   - Fix: Add a "stable secret" class to `generateSecrets()`: generate only when no live value exists (read the existing `.env`, or the live bastion-api variables on Railway), and never rehydrate it. Use `${BASTION_...:-}` in compose, never `:?`, which would abort `docker compose up` for the whole suite. Have bastion-api refuse to start with a plain message that names the `.env` line. Store a key fingerprint on every row: `signing_key_id`, plus a new `pd_hmac_key_id`, so a key change reports `key_changed`, not `hash_mismatch`. Document the key format as a 64-hex Ed25519 seed, wrapped as PKCS8 in code. Add "export and escrow these three keys" to §9.7.

N3. **[infrastructure] MAJOR - Restore detection cannot work, because the seals it compares against are rewound by the same restore.** (Same as stability C and security 2 this round.)
   - Where: §3.4 "Restores", §9.7
   - Why it matters: bastion-api compares the ledger head with the latest seal, but `bastion_ledger_seals` lives in the same Postgres that `pg_dump` restores. After a rewind the head and the latest seal agree, so no `restore` entry is written. The first sign is then an external witness or an auditor holding a newer signed head, which looks like tampering.
   - Fix: At seal time, also write `seals/<org>/<seal_date>.json` (head, seq, signature) to the Bastion bucket. Objects survive a database restore. At boot and in each seal run, compare the database head with the newest seal object. Give `bastion-ledger-seal` a test that restores an older dump and expects `ledger.restored`.

N4. **[infrastructure] MAJOR - The backup mirror copies evidence into the shared bucket on the same MinIO, so it protects nothing and undoes the bucket isolation.**
   - Where: §9.7, §7 `bastion-object-backup`
   - Why it matters: The "backup destination" is `S3_BUCKET` under `BACKUP_KEY_PREFIX` (`apps/worker/src/jobs/backup-database.job.ts:121`, `apps/worker/src/env.ts:55`), which is `bigbluebam-uploads` on the same MinIO. Mirroring to `bastion-mirror/<org>/` there puts restricted HR and pen-test bytes back in the bucket every service can read. If MinIO is lost, the mirror is lost with it. `restore-database.job.ts` restores only Postgres, so "a platform restore can restore both" has no mechanism behind it. `ops.backup_fresh` would certify a mirror that sits on the same disk.
   - Fix: Use a separate destination: `BASTION_BACKUP_S3_ENDPOINT/BUCKET/ACCESS_KEY/SECRET_KEY`, each with a hint, ideally on another provider or host. When it is unset, the job logs "No off-site evidence backup is configured", and `ops.backup_fresh` reports `unprovable`, not pass. Specify the object-restore step as a runbook command or a restore-job extension.

N5. **[infrastructure] MAJOR - The dedicated bucket breaks on S3 and R2 installs, and the worker cannot reach it.** (Overlaps stability G.)
   - Where: §9.1, §9.4, §7.2, §7 (`bastion-object-backup`, `bastion-object-sweep`)
   - Why it matters: The deploy flow offers Amazon S3 and Cloudflare R2 (`promptStorageChoice`). On AWS a literal `bigbluebam-bastion` is a globally unique name almost certainly owned by someone else. Scoped IAM keys usually cannot `makeBucket` (`s3-driver.ts:63-68` calls `makeBucket` when `bucketExists` returns false), so every evidence write would fail. The worker builds and stores the packet in "Bastion's bucket" and runs the mirror and sweep jobs. Neither the worker's compose env nor its catalog entry gets `BASTION_S3_BUCKET`. The worker's `utils/storage.ts` is bound to `S3_BUCKET`, so packets would land in the shared bucket or fail.
   - Fix: Keep the literal default for MinIO. Have the S3/R2 prompt ask for the Bastion bucket name, defaulting to `${S3_BUCKET}-bastion`. At boot, bastion-api runs a put/stat/delete check on the bucket and surfaces a plain error (readiness can stay Postgres and Redis only). Add `BASTION_S3_BUCKET` to the worker's compose block and `env.optional`, and have the Bastion worker jobs use `createBootstrapDriver({ S3_BUCKET: BASTION_S3_BUCKET, ... })`, not `utils/storage.ts`.

N6. **[infrastructure] MAJOR - The #126 `syncNew` design, "fill missing `computed` and `literal` hints on existing services", has no scope limit and would change config across the whole fleet.**
   - Where: §9.4, §12 M0
   - Why it matters: It would add every optional var that is currently absent on any existing service, not just Bastion's URLs: `RATE_LIMIT_*`, `MAX_DOC_*`, `BURN_API_INTERNAL_URL` on bill-api (which turns on the spend gate wherever it was off), and so on. Each variable write triggers a Railway redeploy, so one push to `stable` could redeploy around 20 services at once. Variables an operator deleted on purpose come back on every push.
   - Fix: Make propagation opt-in per hint (`propagate: true`), starting with the `*_API_INTERNAL_URL` and `*_API_URL` computed hints. Never overwrite a variable that is present. Print the planned diff in the CI log, and upsert with `skipDeploys` followed by a single redeploy per service. The M0 "done when" check should assert that the dry-run plan contains only the `BASTION_*` URL additions.

N7. **[infrastructure] MAJOR - The Redis LLM semaphores have no lease and no behaviour defined for a Redis outage, and the stated throughput is off by about 5 to 10 times.** (Overlaps stability F.)
   - Where: §7.3 "LLM fairness", §9.5
   - Why it matters: A bastion-api crash or rolling deploy mid-call leaves a permit held forever: Redis runs `noeviction` and the spec sets no TTL. After three leaks, all Bastion LLM work stops with no error. The numbers: one concurrent call per org at about 10-20 s per call means a 96-row questionnaire takes roughly 16-32 minutes, not 2-4. A 400-call compile takes 1-2 hours. Three service-wide permits give at most about 18 calls per minute, not about 100. UI estimates and the "partial" thresholds would be built on these wrong figures.
   - Fix: Copy `admitLlmCall`'s pattern from `apps/api/src/routes/internal-llm.routes.ts`: a sorted set of random tokens scored by admit time, with stale tokens older than the hold window (90 s, longer than `BASTION_LLM_TIMEOUT_MS`) purged on every admit, and `ZREM` in a `finally`. Fail open when Redis is down, as the proxy does; the proxy's own cap still applies. Restate the throughput from 3 slots and 1 per org, and size the UI estimates from it.

**Minor (infrastructure):**
- Read-replica probes: on a hot standby, long probe statements can be cancelled by recovery conflicts (`max_standby_streaming_delay`). Classify those as a non-drifting infrastructure failure, and record replica lag next to `as_of` in the snapshot.
- `TRUST_PROXY_HOPS`: a self-hosted compose install behind Cloudflare or Caddy needs 2, so say so in `.env.example`. Key the lockout by (ip, room) so a wrong hop count cannot lock out every room at once.
- The `{ kind: 'secret' }` hints have no `value: '<generate>'` or stability `note`, unlike `BLIP_INGEST_PEPPER`, so `railway/env-vars.md` renders them blank.
- If storage is skipped at deploy ("Skip for now"), bastion-api crash-loops on required `S3_*`. Start it anyway and show "Evidence storage isn't set up" instead.
- `nginx.conf` gets the same runtime-resolver block; confirm which stack actually mounts it (`docker-compose.multi.yml`) before adding `127.0.0.11`.
