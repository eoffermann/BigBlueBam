## The defaults-backfill gap (0169)

After applying 0168 the 3 new perms had **zero** rows in `permission_group_defaults`. Querying:

```sql
SELECT pg.legacy_role, COUNT(*) FILTER (WHERE pgd.granted) AS granted
FROM permission_group_defaults pgd
JOIN permission_groups pg ON pg.id = pgd.group_id
JOIN permissions p ON p.id = pgd.permission_id
WHERE pg.is_builtin AND p.id LIKE 'banter.admin_import.%'
GROUP BY pg.legacy_role;
-- (0 rows)
```

**Root cause**: 0156's remediation CROSS JOIN was a one-shot that produced defaults for every permission present *at the time it ran*. Permissions added later via delta migrations (0162, 0168) have no defaults rows, so the resolver evaluates them as "no rule". The Wave F SU-only perms (0160) get away with this because `requires_superuser=true` triggers the SuperUser bypass short-circuit in the resolver — but the `banter.admin_import.*` trio is admin/owner-scoped (NOT requires_superuser) and therefore must have explicit grants.

**Fix** (`0169_banter_admin_import_group_defaults.sql`): inserts 15 rows (3 perms × 5 builtin role groups) using the same role hierarchy as 0156 narrowed to this trio.

**Final tallies after 0169**:

```
 legacy_role | granted | total
-------------+---------+-------
 admin       |       3 |     3
 guest       |       0 |     3
 member      |       0 |     3
 owner       |       3 |     3
 viewer      |       0 |     3
```

Matches the design spec (`docs/plans/slack-import-design.md` §6) exactly.

**Systemic follow-up (out of scope for this wave)**: a future maintenance pass should either teach `build-permission-delta.mjs` to also emit defaults rows for new non-SU perms, or add a generic "missing-defaults backfill" migration that re-applies the 0156 matrix to any perm without rows. Currently every wave that introduces non-SU perms via a delta needs a paired defaults-backfill migration (like 0169). Tracked informally; surface to the operator.
