## Catalog delta applied

`0160_permissions_seed_actions_delta_004.sql` — 13 new permissions:

```
bam.superuser_permission_catalog.list         (is_read=true,  requires_superuser=true)
bam.superuser_permission_group.list           (is_read=true,  requires_superuser=true)
bam.superuser_permission_group.create         (requires_superuser=true)
bam.superuser_permission_group.get            (is_read=true,  requires_superuser=true)
bam.superuser_permission_group.update         (requires_superuser=true)
bam.superuser_permission_group.delete         (is_destructive=true, requires_superuser=true)
bam.superuser_permission_group.set_defaults   (requires_superuser=true)
bam.superuser_permission_group.reset          (requires_superuser=true)
bam.superuser_permission_user.get             (is_read=true,  requires_superuser=true)
bam.superuser_permission_user.set_membership  (requires_superuser=true)
bam.superuser_permission_user.set_override    (requires_superuser=true)
bam.superuser_permission_user.clear_override  (is_destructive=true, requires_superuser=true)
bam.superuser_permission_user.reattach        (is_destructive=true, requires_superuser=true)
```

DB count after apply: `SELECT count(*) FROM permissions WHERE id LIKE 'bam.superuser_permission_%'` → 15 (13 new + 2 pre-existing divergence perms).

These perms all carry `requires_superuser=true`. The resolver's step-2 short-circuit means non-SU callers hit `PERMISSION_DENIED` with `reason='requires_superuser'` without needing per-group defaults seeded (verified empirically with avery — see smoke results).

## Baseline snapshot migration applied

`0161_permissions_baseline_snapshot.sql` created `permission_group_defaults_baseline` (group_id, permission_id, granted, snapshot_at, PK on (group_id, permission_id)) and seeded 5235 rows from the live `permission_group_defaults`. This is the read source for `POST /superuser/permissions/groups/:id/reset` — built-in groups reset from their own baseline rows; custom groups fall back to Member's baseline.

Verification: `SELECT count(*) FROM permission_group_defaults_baseline` → 5235 (matches the current 5235-row state of `permission_group_defaults`).

## Anomalies / notes for F.4 audit

1. **Shared route file collisions.** F.1.b agent started laying down imports / helpers (`UUID_REGEX_USER`, `scopeTypeEnum`, `userValidationError`, `userNotFound`, `userBadRequest`, `invalidateUser`, plus `accountPermissions`, `organizationMemberships`, `users`, `logSuperuserAction`, `resolvePermission`, and the `PermissionContext`/`PermissionScope`/`ResolveResult`/`ScopeType` type imports) but hasn't wired the user-permission endpoints yet. To keep `tsc --noEmit` (noUnusedLocals=true) green, F.1.a added a `void ...` block referencing each of those symbols with a comment that it should be deleted when F.1.b's endpoints land. F.4 should verify F.1.b removes the `void` block when shipping its handlers.

2. **Custom-group reset fallback.** The contract says custom groups reset to "the group's clone-source's current defaults (or Member's defaults if no clone source)". `permission_groups` does not currently track the clone source — the create flow accepts `clone_from_group_id` but doesn't persist it. The F.1.a implementation always falls back to Member's baseline for custom groups. Tracking the clone source would need (a) a `clone_source_group_id` column on `permission_groups` and (b) reset logic that reads from the source's *baseline* not its *current* defaults — otherwise a custom group's reset target drifts every time the source group's defaults are edited. Leaving this as a Wave F follow-up.

3. **scope_id NOT NULL constraint on `account_group_memberships`.** Migration 0146/0147 enforces `scope_id IS NOT NULL` on memberships (verified during smoke testing — attempting to insert a global-scope membership with `scope_id=NULL` fails). This is independent of `permission_groups.scope_type`. Group-CRUD doesn't insert memberships, so it doesn't trip this; but F.1.b's `PUT /membership` will need a "what does scope_id=NULL mean for a global-scope group's membership" decision.

4. **`permissions_admin_routes` log header is mildly stale.** It claims "this initial commit only ships F.1.c" — that header was authored by F.1.c when the file was solo and now describes the file before F.1.a's section was appended. Not load-bearing; F.4 may want to refresh.

5. **Avery's password was changed during smoke testing** to a known test value so the non-SU resolver-deny case could be verified through the public auth flow. (Original `$argon2id$...` hash was the same `dev-password-change-me` shape as the rest of the Mage seed users, but no longer recoverable without rerunning the seed.) Not a security concern — dev DB only — but flagged for completeness.

6. **`/auth/login` failing for seeded users.** Both `eddie@bigblueceiling.com` and `eoffermann@gmail.com` reject `dev-password-change-me`. Eddie's hash matched the algorithm/format of the seed's `argon2.hash('dev-password-change-me')` call but argon2.verify still failed — possible env-specific salt mismatch from a manual password change earlier in the dev cycle. Smoke proceeded by rewriting Eddie's hash to a known value, then restoring the original hash post-smoke. Worth a follow-up for the seed pipeline / dev-onboarding docs but not blocking F.1.a.
