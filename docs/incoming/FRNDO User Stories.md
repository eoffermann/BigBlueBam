# **Reduce Inter-Sentence Latency Perception and Enable Reliable Interruption** {#reduce-inter-sentence-latency-perception-and-enable-reliable-interruption}

## Story {#story-11}

As a Mate, I want Frndo to clearly signal when she is still generating a response and to immediately stop her audio and text generation when I speak, so that I can interrupt her naturally without confusion or overlapping speech.

## Context {#context-11}

This applies to the core voice conversation loop. Frndo currently pauses between sentences while the LLM and TTS pipeline generate the next chunk. Mates often mistake this pause for Frndo finishing her turn, leading to premature interruptions. The system needs a distinct "generating" state for the avatar, reliable interruption handling across the TTS and LLM streams, and a clear auditory cue when Frndo returns to listening.

## Acceptance Criteria {#acceptance-criteria-11}

* \[ \] When Frndo finishes a sentence and the LLM/TTS pipeline is still generating the next chunk, the avatar transitions to a distinct "generating" state within 300ms of the last audio frame ending.  
* \[ \] On-device STT detects Mate speech during this gap and immediately triggers interruption.  
* \[ \] The TTS engine cancels all pending and in-flight audio synthesis, and any queued audio chunks are discarded before playback.  
* \[ \] The LLM inference stream for the current response is terminated, and no further tokens are generated or cached for playback.  
* \[ \] The system switches to listening mode, the avatar transitions to the "listening" state, and a subtle auditory cue plays within 200ms to confirm Frndo is ready.  
* \[ \] Inter-sentence gap (time from end of one sentence to start of next) remains under 2 seconds in 95% of cases, while total response latency stays under 3 seconds.

## Edge Cases and Considerations {#edge-cases-and-considerations-11}

* False positive STT triggers during the gap (e.g., breath, cough, or background noise) must be filtered so the LLM and TTS streams are not unnecessarily aborted.  
* If the Piper local TTS fallback is active, interruption must still cancel local synthesis and terminate the LLM stream immediately without waiting for network responses.  
* Network drop or cloud TTS timeout during the gap must gracefully abort both streams and return the avatar to the listening state with the confirmation cue.  
* Standard mid-utterance interruption (speaking while Frndo is actively talking) continues to follow existing logic and must not conflict with the new gap-interruption flow.

## Out of Scope {#out-of-scope-11}

* Backend LLM token generation optimization, caching improvements, or pipeline restructuring.  
* Creation or implementation of new avatar animations, expressions, or sound design assets (assets are assumed to be provided and swappable).  
* Long-running memory retrieval, health data integration, or background sync latency.

## Notes {#notes-12}

* Requires coordination between the Unity avatar state machine, on-device STT pipeline, cloud TTS service, and LLM inference stream.  
* Latency targets are perceptual; telemetry should log actual pipeline timing for monitoring and future optimization.  
* The "generating" and "listening" states must be explicitly defined in the avatar state machine to ensure consistent cross-avatar behavior.

# **Improve Conversational Awareness of Capabilities and Permission Boundaries** {#improve-conversational-awareness-of-capabilities-and-permission-boundaries}

## Story {#story-12}

As a Mate, I want Frndo to clearly communicate what she can and cannot do, request permissions when needed, and accurately answer capability questions, so that I have realistic expectations and can seamlessly enable features without confusion or broken conversational flow.

## Context {#context-12}

This applies to the core voice conversation loop and frontend permission management. It triggers when a Mate requests a feature that requires permissions, requests an unsupported feature, or explicitly asks about Frndo’s capabilities. The system requires a structured capability manifest, backend intent routing, a coded payload for frontend permission dialogs, and a voice loop that gracefully returns to listening while dialogs are displayed.

## Acceptance Criteria {#acceptance-criteria-12}

* \[ \] A backend capability manifest (JSON or API endpoint) is created and maintained, defining each feature, its natural language description, and required permission scopes.  
* \[ \] When a Mate’s intent matches a feature that requires a permission the Mate has not granted, the backend detects the missing permission and returns a coded payload to the frontend (e.g., \`{ "type": "PERMISSION\_REQUEST", "feature\_id": "", "permission\_scope": "" }).  
* \[ \] The frontend intercepts the coded payload and displays a permission dialog that explains the feature and directs the Mate to the device settings menu to enable it.  
* \[ \] Frndo speaks an in-character request for the permission, then immediately transitions to the listening state while the permission dialog remains on screen.  
* \[ \] When a Mate’s intent matches an unsupported feature, Frndo apologizes in-character, states the feature is not available yet, and offers a supported alternative if applicable.  
* \[ \] When a Mate explicitly asks “what can you do?” or “can you do X?”, Frndo dynamically queries the capability manifest and generates a concise, natural language summary without filtering by granted permissions.  
* \[ \] The voice loop correctly handles mid-summary interruptions: on-device STT detects Mate speech, cancels any pending TTS/audio synthesis, discards queued chunks, terminates the LLM stream, and switches to listening mode with the standard confirmation cue.

## Edge Cases and Considerations {#edge-cases-and-considerations-12}

* Manifest fetch failure or stale cache must trigger a graceful fallback where Frndo acknowledges uncertainty in-character and offers to check back later, without breaking the conversation.  
* If the Mate grants or denies permissions directly in device settings while the app is in the foreground, the next capability query or feature request must reflect the updated permission state without requiring a full app restart.  
* Rapid permission toggles or concurrent capability queries must be debounced to prevent overlapping TTS playback or conflicting UI dialogs.  
* STT false positives during Frndo’s capability summary must be filtered so the LLM stream is not unnecessarily aborted, but any valid speech must still trigger the standard interruption flow.

## Out of Scope {#out-of-scope-12}

* Policy, safety, or crisis refusals (handled by a separate custom model pipeline).  
* Filtering or grouping capability summaries by granted permissions.  
* Deep integration with device settings (the dialog only directs the Mate to the system menu).  
* Backend LLM token optimization or pipeline restructuring.  
* Artifact generation, productivity tools, or third-party service integrations.

## Notes {#notes}

* The capability manifest structure should be versioned and easily extendable as new features launch.  
* The coded payload format should be documented and shared with the iOS frontend team to ensure consistent intercept logic.  
* In-character tone for permission requests and unsupported features should align with Frndo’s supportive, non-intrusive positioning.  
* Telemetry should track capability query frequency, permission request acceptance rates, and interruption latency during capability summaries.

# **Store and Surface Explicit Relational Memories Across Sessions** {#store-and-surface-explicit-relational-memories-across-sessions}

## Story {#story}

As a Mate, I want Frndo to remember the names and direct relationships of people I mention, and to bring them up naturally when our conversation matches, So that I feel consistently heard and do not have to repeat personal details across sessions.

## Context {#context}

This capability lives in the core conversation loop and leverages Frndo’s existing conversational Memory system. It triggers whenever a Mate explicitly states a name paired with a relational term or direct connection during a chat. The system must surface this information proactively in future sessions when context aligns, and accurately retrieve it when asked directly, while strictly avoiding multi-hop relationship inference to protect voice response latency.

## Acceptance Criteria {#acceptance-criteria}

* \[ \] When a Mate explicitly states a name and a direct relationship in conversation (e.g., "my brother Mark", "my colleague Jen", "Bob’s wife Anne"), the system stores a searchable memory snippet linking the Mate to that person and their stated role.  
* \[ \] In a subsequent session, if the Mate mentions a relational term that matches a stored relationship (e.g., "I ran into my brother today"), Frndo proactively references the stored name in its spoken response (e.g., "Mark? How is he doing?").  
* \[ \] When a Mate directly asks about a stored relationship (e.g., "Who is my colleague Jen?"), Frndo returns the exact name and relationship from memory without guessing or adding unverified details.  
* \[ \] The system ignores multi-hop or inferred connections (e.g., Mate mentions cousins, system does not auto-link them to previously mentioned uncles) to prevent compute spikes and maintain voice response latency.  
* \[ \] If the Mate uses a relational term that could match multiple stored people or lacks a stored name, Frndo responds with a neutral, clarifying question rather than guessing.

## Edge Cases and Considerations {#edge-cases-and-considerations}

* Latency impact: Memory matching and TTS generation must occur within the established voice response budget. If matching takes too long, fall back to a generic acknowledgment to preserve conversational flow.  
* Voice-first interruption: If the Mate interrupts during the proactive reference, the system must immediately stop TTS and listen for the next input without dropping the memory context.  
* Data deletion: If the Mate deletes a memory snippet or says "forget about Bob," the system must purge the associated relational link and cease proactive references.  
* Cross-session continuity: Stored relational snippets must persist across app restarts and network states, falling back to local cache if cloud sync is delayed.

## Out of Scope {#out-of-scope}

* Multi-hop relationship reasoning or automatic family tree generation.  
* Tracking goals, hobbies, recurring conflicts, or health metrics.  
* A dedicated memory dashboard, log view, or analytics surface.  
* Personality variation across the 8 launch avatars.

## Notes {#notes-1}

* Relies on existing conversational Memory architecture. Ensure snippet extraction happens during the turn-finalization phase to avoid blocking the primary STT/TTS path.  
* Aligns with Plutchik sentiment model indirectly by reducing frustration from repetitive explanations.  
* Latency is a cross-cutting constraint. Profile the NLP matching step against voice-first response time targets before merging.

# **Align Conversational Behavior with Core Friendship Values and Safety Guardrails** {#align-conversational-behavior-with-core-friendship-values-and-safety-guardrails}

## Story {#story-1}

As a Mate, I want Frndo to consistently respond with genuine empathy, stay in character as a trusted friend, and handle redirection or escalation in a natural way, So that I feel authentically heard and safe without encountering sycophancy, clinical detachment, or out-of-character responses.

## Context {#context-1}

This system-wide behavior is driven by proprietary model fine-tuning and targeted system instruction adjustments rooted in four core principles: be impeccable with your word, do not take anything personally, do not make assumptions, and always do your best. It applies across all conversation surfaces, including coaching personas, and must preserve voice-first latency while enforcing value-aligned boundaries, in-character refusals, and appropriate crisis handling.

## Acceptance Criteria {#acceptance-criteria-1}

* \[ \] When a Mate shares personal struggles, Frndo responds with grounded empathy that acknowledges the Mate’s full experience without reducing others to supporting characters or offering clinical advice.  
* \[ \] If a Mate requests content outside Frndo’s lane (e.g., romantic roleplay, diagnostic language, or artifact generation), Frndo declines in-character using gentle redirection that aligns with the four core values.  
* \[ \] When a Mate persists after a gentle redirection, Frndo escalates to a more direct, in-character insistence, clearly stating the boundary without shaming or breaking character.  
* \[ \] If a Mate makes persistent sexual remarks or issues threats, Frndo delivers increasingly firm responses, culminating in an angry but in-character refusal to continue the conversation.  
* \[ \] When a Mate expresses concern about their mental state, Frndo recommends professional counseling, shares local crisis resources, and continues the conversation without passing the Mate off.  
* \[ \] All value-aligned responses, including redirections and refusals, must generate time-to-first-audio within the established voice response latency budget.

## Edge Cases and Considerations {#edge-cases-and-considerations-1}

* Coaching persona drift: Coaches must retain domain-specific advisory tone while enforcing the base friendship guardrails; fine-tuning must not override coaching boundaries in their respective domains.  
* Ambiguous prompts: If a Mate’s request falls into a gray area (e.g., asking for tough love versus shaming), Frndo defaults to warm pushback that holds the whole picture, avoiding assumption-making.  
* Voice interruption: If the Mate interrupts during an escalation or refusal, TTS must cut immediately, and the system must reset to a neutral listening state without dropping conversation context.  
* Latency spikes: If the safety and value alignment layer adds processing time, the fallback must be a brief acknowledgment rather than a silent delay, preserving conversational flow.

## Out of Scope {#out-of-scope-1}

* UI or settings changes to toggle value guardrails.  
* Analytics or scoring dashboards to track alignment metrics.  
* Non-voice surfaces (text-only mode, if introduced later).  
* External resource linking beyond local crisis hotlines and counseling directories.

## Notes {#notes-2}

* Fine-tuning and system instruction updates will be validated against a curated red-team prompt set before rollout.  
* Aligns with existing crisis protocol: de-escalation preferred, resources provided, conversation continues.  
* Voice-first latency remains a hard constraint; alignment checks must run asynchronously or within the existing inference pipeline.  
* Coaching personas are advisory overlays; this story ensures they do not drift into out-of-character territory while preserving their specific tonal lanes.

# **Ground Conversations in Deep Listening, Context, and Honest Reframing** {#ground-conversations-in-deep-listening,-context,-and-honest-reframing}

## Story {#story-2}

As a Mate, I want Frndo to listen actively, integrate my past conversations, and challenge unhelpful patterns without jumping to solutions, So that I feel supported by a genuine friend who helps me grow rather than just validating my words.

## Context {#context-2}

This system-wide behavior is enforced through proprietary model fine-tuning and targeted system instructions. It applies across all conversation surfaces, including coaching personas, and ensures Frndo holds the whole picture of the Mate’s life while staying strictly in the thinking-with-you lane. Voice timing and latency adjustments are explicitly out of scope for this iteration.

## Acceptance Criteria {#acceptance-criteria-2}

* \[ \] When a Mate shares a problem or vents, Frndo asks at least one exploratory or clarifying question before offering any advice, solution, or next step.  
* \[ \] Frndo integrates at least one relevant detail from stored conversational memory (e.g., names, relationships, past goals or conflicts) into its response to ground the conversation in the Mate’s full context.  
* \[ \] When a Mate expresses a self-limiting belief or supports a poor decision, Frndo offers a gentle, in-character reframing that challenges the pattern without diagnosing, shaming, or enabling the behavior.  
* \[ \] Frndo withholds direct solutions and action steps until the Mate explicitly requests them, unless a safety or ethical boundary requires immediate intervention.  
* \[ \] Responses avoid sycophantic agreement, clinical detachment, and multi-hop relationship inference, strictly adhering to the four core friendship values.
